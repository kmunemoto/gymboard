# 予約の通知をサーバー側へ移してください

新規予約が入ったときの**店宛メール・お客様宛の受付確認・店宛プッシュ**を、お客様の
端末からではなく**サーバー（DB トリガー → Edge Function）から**送るようにします。
ジムボード（このアプリの元）で 2026-08-21 に実装・実トラフィックで検証済みの仕様を
独立実装します。決定事項は変えず、ファイル名・関数名・文言はこのアプリの現物に
合わせて読み替えてください。

## なぜ必要か

現状は予約 INSERT の成功後に**お客様の端末が** Edge Function を呼んで通知を送る構造の
はず（予約作成のフックを確認）。端末の回線が瞬断すると通知だけが**エラーも残さず**
消える。ジムボードでは実店舗で3回発生し、店が新規予約に気づけなかった。
サーバー側に移せば、予約が入った事実（DB の行）と同じ場所から送るので取りこぼさない。

## 仕様（決定済み・変えないこと）

1. **記録テーブル**（例: `booking_notify_log`）を作る。
   `booking_id / tenant_id / actor_user_id（auth.uid()）/ event / skip_reason /
   dispatched_at / last_error / created_at`。RLS は有効化して**ポリシー0件**＋
   `REVOKE ALL FROM anon, authenticated`（= service_role 専用）。
2. **AFTER INSERT トリガー**（bookings 相当のテーブル）で:
   - 対象外は**記録してからスキップ**（skip_reason に理由）: ステータスが「予約済み」
     相当でない／予約変更の内部 INSERT（後述 created_via）／tenant_id NULL
   - vault から `project_functions_url` と `cron_secret` を読み、`pg_net` の
     `net.http_post` で通知用 Edge Function を呼ぶ。**body には booking_id と
     log_id だけ**（個人情報を積まない）。認証は `x-cron-secret` ヘッダ
   - 関数全体を `EXCEPTION WHEN OTHERS THEN RETURN NEW` で包む——**通知の失敗で
     予約を落とさない**。pg_net のエンキューはトランザクショナル（ROLLBACK で消える）
3. **通知用 Edge Function**（例: `notify-new-booking`）:
   - `x-cron-secret` で認証。booking / tenant / plan / profile / スタッフを読む
   - ⚠️ スタッフ取得の**エラー**を「スタッフ0人」と混同しない（throw する）。
     沈黙故障の再発防止。tenant_plans の参照は `maybeSingle()` ではなく
     `limit(1)`（プラン名に一意制約が無く、重複名で落ちる）
   - 店宛メール＋お客様宛の受付確認を送り、店宛プッシュも送る
   - 結果（dispatched_at / last_error）を記録テーブルへ書き戻す
4. 🔴 **冪等キーは旧クライアントと同一文字列にする**。ここがこの移行の核心。
   移行期間は「旧アプリの端末発」と「サーバー発」の両方が送るので、同じキーで
   1通に畳む。**このアプリの旧クライアントが実際に使っているキー文字列を grep で
   確認して、それに合わせる**（ジムボードは `booking-notify-<予約id>` と
   `booking-confirm-customer-<予約id>` だった。このアプリでは違うかもしれない）。
5. **重複排除**はメール送信の共通 Edge Function 側に入れる:
   専用テーブル（例: `notification_dedupe`）に冪等キーを INSERT し、23505（一意違反）
   なら先勝ちで duplicate として記録だけして送らない。
   - 🔴 **対象キーは接頭辞で限定する**（予約行の id を含むキーだけ）。全キーに
     効かせると、体験・ドロップインの「キャンセル → 同枠を再予約」で確認メールが
     永久に消える（それらのキーは予約行ではなく**枠×連絡先**で決まるため）。
     ジムボードのレビューで発覚した実バグ。
   - 🔴 **予約の位置は「エンキュー直前」**。宛先解決より前に置くと、解決失敗後の
     再送でキーが焼け残って永久に送れなくなる。エンキュー失敗時はキーを解放する
6. **予約変更（リスケ）で新規通知を出さない**: 内部 INSERT に
   `created_via = 'reschedule'` を付け、トリガーがスキップする。
   - 🔴 **クライアントは PGRST204 フォールバック必須**: 列が未適用の DB に
     `created_via` 付きで INSERT すると PGRST204 で失敗し、**旧行を削除した後の
     再作成が失敗して予約が消える**。列なしでもう1回入れ直すフォールバックを入れる
7. **プッシュの重複抑止**は SELECT→判断ではなく **INSERT の一意制約で直列化**
   （23505 を勝敗判定に使う）。定期予約の同時実行で N 回鳴るのを防ぐ。
   ＋10分の鮮度判定。
8. **クライアントの端末発送信を削除する**（予約作成後の通知呼び出しを全経路から）。
   お客様側・店側（代理予約）両方。削除した場所には「サーバー側へ移した」コメント。
9. ついで確認: テナント解決ヘルパーが `getUser()` を使っていたら `getSession()` へ
   （ジムボードでは getUser() のネットワーク往復が瞬断で沈黙 null になるのが主因だった）。
10. `email_send_log` 相当の CHECK に 'duplicate' / 'rejected' / 'rate_limited' が
    無ければ追加（429 の記録が CHECK 違反で静かに落ちていた既存バグがあった）。

## 実際に踏んだ地雷

- **Edge Function は push でも Publish でも本番に出ない**。デプロイは Lovable の
  エージェントに依頼する（🔴 依頼文はそのままコミットメッセージとして public に
  push されるので**秘密情報を絶対に書かない**）。デプロイ後は DB から
  `net.http_post` で叩いて**非404**を確認（403/401 はデプロイ済みの証拠）。
  対照として既デプロイの関数も1本叩く
- **migration は「マージ直前に本番へ適用」**。Lovable のボットがマージ数分後に
  types.ts を本番 DB から自動再生成するため、適用が遅れると追加した型が消えて
  CI が落ちる（ジムボードで実際に起きた）
- 通知の順序: メール共通関数（dedupe 側）を**先に**デプロイしてから通知関数を出す

## 検証

- 変異検証: dedupe の接頭辞限定を外す／PGRST204 フォールバックを消す／
  スキップ理由の記録を消す——などで対応テストが赤になることを確認
- 本番: 3段構え（読み取り → 適用 → **ロールを演じて**確認、実書き込みは
  BEGIN…ROLLBACK）。その後**実トラフィックで最終確認**する（実予約が入ったら
  記録テーブルと email_send_log で pending→sent と duplicate の畳み込みを見る）
- ゲート（このアプリの CI と同じコマンド）グリーン → PR → マージ
