# 営業時間と予約枠の連動

最終更新: 2026-08-20

> **2026-08-20 追記**: 曜日別の営業時間と定休日、および「何日先まで予約を受けるか」を足した。
> このファイルは**全曜日共通だった時代の経緯**を残したもので、いまの仕様は
> `mem/features/business-days-and-booking-window.md` が正。
> 下の関数はすべて `weekday` を受け取れるようになっている（省略時は従来どおり）。

## 唯一の解釈者は `src/lib/businessHours.ts`

`tenants.operating_hours` から予約枠の範囲を作るのは、この1ファイルだけ。
画面側で `600` や `1260` のような分の数値を書かないこと。
`src/test/businessHours.test.ts` が直書きの再発を検査する（変異16種で確認済み）。
曜日別・定休日ぶんの検査は `src/test/businessDays.test.ts`（変異6種）。

| 関数 | 用途 | 終端 |
|---|---|---|
| `bookingSlotMinutes(hours, slotMinutes, weekday?)` | **予約枠**（お客様・予約を追加・体験・ドロップイン） | `終業 − 枠の長さ` |
| `businessGridMinutes(hours, weekday?)` | 週表示の行・ブロック枠の**開始** | `終業 − 15分` |
| `blockEndMinutes(hours, startMin, weekday?)` | ブロック枠の**終了** | `終業`ちょうど |

`weekday` を渡すとその曜日の営業時間で並ぶ（定休日なら空配列）。
省略すると `start`/`end`（＝開いている曜日全体を包む**包絡線**）で並ぶ。

予約枠だけ枠の長さを引くのは、**施術が終業までに終わる必要がある**から。
ブロック枠（休憩・設営）は施術ではないので終業まで置ける。

## 🔴 何が起きていたか（2026-08-15 に宗本さんが実機で発見）

営業時間を 23:00 にしているのに、予約は **21:00 スタートが最後**だった。

原因は **6箇所すべてが別々の数字を直書きしていた**こと。

| 画面 | 直書き | 出ていた範囲 |
|---|---|---|
| 予約を追加（TrainerSchedule） | `600 → 1260` | 10:00〜21:00 |
| 体験予約（TrialBooking） | `600 → 1260` | 10:00〜21:00 |
| ドロップイン（DropInBooking） | `600 → 1260` | 10:00〜21:00 |
| 週表示（TrainerSchedule） | `600 → 1335` | 10:00〜22:15 |
| ブロック枠 開始（TrainerSchedule） | `600 → 1335` | 10:00〜22:15 |
| ブロック枠 終了（TrainerSchedule） | `→ 1290` | 〜22:30 |

**お客様側（CustomerBooking）だけが営業時間を読んでいた。** そのため
「お客様は 22:00 で予約できるのに、店の予約追加画面には 21:00 までしか出ない」
という食い違いが起きていた。設定画面には「お客様の予約画面に表示される営業時間」と
書いてあるのに、**設定が効いていたのは1画面だけ**だった。

DB は正しかった（`{"start":"10:00","end":"23:00"}`）。保存はできていて、読む側が無視していた。

### 分を捨てていた

`CustomerBooking` の `parseHour` は `"22:30".split(":")[0]` で**時だけ**を取り、分を捨てていた。
設定画面は30分刻みで保存できるので `22:30` → `22:00` になる。
`parseTimeToMinutes` は分まで解釈する。

## 公開ページは `get_tenant_public` 経由

体験予約・ドロップインは anon なので、**RPC が返さない列は存在しないのと同じ**。
`operating_hours` を返していなかったので、そもそも営業時間を知る手段が無かった
（migration `20260815010000`）。

⚠️ `RETURNS TABLE` の列を増やすのは戻り値の型変更なので `CREATE OR REPLACE` では通らない。
**`DROP` してから作り直す。DROP すると GRANT が消えるので明示的に戻すこと**
（戻し忘れると本番で anon が 42501 になる。テストが GRANT 行の存在を検査している）。

## 既定値

`operating_hours` 未設定のテナントは **10:00-21:00**（`DEFAULT_OPEN_MINUTES` /
`DEFAULT_CLOSE_MINUTES`）。終業が開店以前という不正な設定も既定値に落とす
（そうしないと枠が1つも出ず、画面が空になる）。

テストは既定値を**実値で固定**している。`DEFAULT_*` 同士で比べると同語反復になり、
定数を書き換えてもテストが両辺とも動いて気づけない（変異検証で実際にすり抜けた）。

## 週タイムライン（WeekTimelineView）も直書きだった（2026-08-18 に追加で発覚）

最初の修正（PR #310）では**タイムライン表示を漏らしていた**。

```js
const START_HOUR = 9;
const END_HOUR = 22; // 22:00 まで（最終予約終了想定）
```

予約自体は取れるようになったのに、**予定表が 22:00 より下と 9:00 より上へスクロールできない**
という報告で判明。枠を作る箇所（6つ）は直したが、**枠を「見る」箇所**が別にあった。

`timelineHourRange(operatingHours, bookingMinutes)` に寄せた。軸は「時」単位なので
開店は切り捨て・閉店は切り上げる（10:30-22:30 → 10:00-23:00 の軸）。

🔴 **営業時間の外にある予約も軸に含める。** 営業時間を狭めると、それ以前に入っていた
予約が軸からはみ出して**画面から消える**（負の座標に描かれ、スクロールしても出てこない）。
予約が消えたように見えるのは実害が大きいので、軸のほうを広げる。

### 到達不能な保険は置かない

`if (endHour <= startHour) endHour = startHour + 1;` という保険を書いたが、
`resolveBusinessMinutes` が `close > open` を保証するので**到達できなかった**。
変異検証で「消しても赤くならない」と分かったので削除し、
不変条件（どんな入力でも `endHour > startHour`）をテスト側で総当たりで検査している。
**テストで到達できない防御コードは、動く保証が無いまま「守っているつもり」になる。**

## テストの遅さで巻き添えが起きる

`trainerClientFeatureGates.test.tsx` は**最初の1件だけ**が既定の5秒に乗ることがある
（TrainerClientDetail が recharts 等を引くため。2件目以降は約150ms）。
タイムアウトすると mock が中途半端に残り、**次のテストまで巻き添えで落ちる**。
2026-08-18 に2回踏んだので、この1件だけ 20 秒に緩めた。
遅いのは初回のモジュール読み込みであって、検査対象の挙動ではない。
