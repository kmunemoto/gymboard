# 時間帯別の同時受け入れ数（2026-08-21）

`tenants.booking_capacity`（同じ時間帯に店として受けられる予約の数）を、
**曜日×時間帯で上書き**できるようにした。

## なぜ必要か

`booking_capacity` は1つの値しか持てないが、実際の店は時間帯で受けられる数が変わる:

```
平日の昼   スタッフ2人 → 同時2件
平日の夜   1人で回す   → 同時1件
土曜の午前 応援あり     → 同時3件
```

1つの値しか持てないと、**いちばん少ない時間帯に合わせるしかない**（昼の空きが
埋まらない）か、**いちばん多い時間帯に合わせる**（夜に対応できない予約が入る）。

## 予約回数の制限（GB003）との違い

| | 何を絞るか | 誰を見るか |
|---|---|---|
| 予約回数の制限（`booking_frequency_limits`） | **お一人が**取れる回数 | 予約者を見る |
| 容量の帯（`booking_capacity_windows`） | **その時間の枠そのもの** | 予約者に関係ない |

目的が違うので**別テーブル**。1つの表に混ぜると、行を見ても「誰への制限か /
店の容量か」が区別できなくなる。設定画面でも並べて置き、説明文で違いを示している。

## 解決の順序

```
1. 予約の開始時刻に当てはまる有効な帯を探す
2. 当てはまる帯があれば、その中の最小の capacity を採る
3. 1つも当てはまらなければ tenants.booking_capacity（従来どおり）
```

🔴 **複数マッチは最小値（厳しいほうが勝つ）。**
「平日は2件」と「金曜の夜は1件」が重なったら1件。最大値を採ると、**絞るつもりで
足した帯が広い帯に負けて効かない**という「設定したのに効かない」事故になる。
予約回数の制限が AND（すべて満たす）なのと同じ考え方。

時間帯は [start, end) の半開区間。18:00-21:00 の帯は 18:00〜20:59 開始に効き、
21:00 開始には効かない。

⚠️ **予約回数の制限（booking_frequency_limits）は 2026-08-21 から閉区間 [start, end]**
で、意図的に規則が違う（`mem/features/booking-frequency-limits.md` の
「終端は含む」参照）。帯は「その時間に居るスタッフの数」なので半開のまま
（12時に帰る応援の帯を 12:00 開始に効かせてはならない）。

## 1箇所にまとめる

DB は `resolve_booking_capacity(tenant_id, booking_date)` に切り出し、
`check_booking_overlap` はそれを呼ぶだけにした（トリガーだけ直して呼び出し側を
直し忘れる、が起きにくい）。クライアントは `src/lib/bookingCapacity.ts` の
`resolveSlotCapacity`。`src/test/bookingCapacity.test.ts` が両者の一致を見張る。

## 体験・ドロップイン（公開ページ）にも効く

`check_booking_overlap` は `bookings` と `trial_bookings` の**両方**のトリガーから
呼ばれるので、DB 側は自動的に効く。画面側にも同じ判定を持たせないと
「空きと見せて拒否」になるため、anon から読める RPC
`get_tenant_capacity_windows` を用意した（表そのものは anon に開けない。
`get_tenant_booking_questions` と同じ形）。RPC は**有効な帯だけ・営業中の店だけ**を返す。

判定を持つ画面は4つ:
`CustomerBooking` / `TrainerSchedule`（会員・店側）、
`TrialBooking` / `DropInBooking`（公開ページ、RPC 経由）。

## 画面

- 設定 → 「時間帯別の同時受け入れ数」（`TrainerCapacityWindows.tsx`）。
  営業時間カードの直後に置く（同じ概念の設定なので）
- 帯を1つも作らなければ、営業時間の「同時に受けられる予約数」が全時間に効く
  （＝この機能を入れる前と完全に同じ）
- 保存は**挿入 → 差分削除**の順。削除→挿入だと挿入だけ失敗したときに帯が全部
  静かに消えて「制限なし」に戻る（`TrainerBookingLimits` と同じ理由）
- 読み込み失敗は「帯0件」と区別して保存ボタンを塞ぐ（`loadFailed`）

## テーブル

```
booking_capacity_windows(id, tenant_id, weekdays int[], start_time, end_time, capacity, enabled, …)
  CHECK cardinality(weekdays) >= 1 AND weekdays <@ ARRAY[0..6]
  CHECK capacity BETWEEN 1 AND 99
  CHECK end_time > start_time  -- ゼロ埋め "HH:MM" は辞書順＝時刻順
```

- `capacity = 0` は許さない。「その帯は受け付けない」は**営業時間・定休日で表すもの**で、
  容量0で表すと「空き0件」と「営業していない」が画面上で区別できなくなる
- 開始に `"24:00"` は許さない／終了だけ許す（終端専用の値。他の設定表と同じ）
- ⚠️ `array_length('{}',1)` は NULL を返し CHECK を素通りするので `cardinality` を使う
  （`booking_frequency_limits` で踏んだ）

## RLS

- 読みは**同じジムの人全員**（お客様の予約画面が枠の判定に使う）。
  店の容量は「誰への制限か」を含まないので、`booking_frequency_limits` の
  個別ルールのようなプライバシーの問題は無い
- 書けるのは owner / trainer。anon には表を開けず、RPC だけ

## 本番適用（2026-08-21）

適用済み（`20260821030000_booking_capacity_windows.sql`）。実挿入で確認
（すべて ROLLBACK。owner / お客様2名 / anon を演じ分け）:

| ケース | 期待 | 結果 |
|---|---|---|
| 帯なし → `tenants.booking_capacity`(=1) | 1 | ok |
| 広い帯(2件)だけマッチする月曜19時 | 2 | ok |
| 広い帯(2)＋狭い帯(1)が重なる金曜19時 | **1（最小）** | ok |
| 金曜21:00（狭い帯の終端・排他） | 2 | ok |
| 金曜18:00（狭い帯の始端・含む） | 1 | ok |
| 土曜（曜日が合わない）/ 月曜8時（帯の前） | 既定1 | ok |
| **既定1の店で、帯が2件を許す時刻に2人が予約** | 2件とも通る | ok |
| **既定2の店で、帯が1件に絞る時刻に2件目** | 満枠で拒否 | ok |
| `enabled=false` の帯 | 効かない | ok |
| お客様: 読める / UPDATE は0行 | | ok |
| anon: 表は permission denied / RPC は有効な帯だけ1件 | | ok |

適用後、`booking_capacity_windows` は **0件**（どの店も帯なし＝従来どおり）。
`tenants.booking_capacity` も変更なし。

### ⚠️ RLS 下の検証で件数を数えるときはロールに注意（2026-08-21）

「2件通るはず」の検証で **1件しか見えず、失敗したかと思った**。原因は
count をお客様ロールのまま実行していたこと（`bookings` の SELECT ポリシーで
自分のぶんしか見えない）。**数えるときはオーナーに戻す。**

## 検討したがやらなかったこと

- **帯で営業時間そのものを表す**（capacity 0 = 閉店）: 営業時間・定休日と二重管理に
  なる。上の CHECK で 0 を弾いている
- **占有の終わりまで見て帯を当てる**: 18:50 開始・60分の予約が 19:00 の帯にも
  かかる、という判定。説明できない設定は現場で使われないので、開始時刻だけを見る
- **スタッフ数からの自動算出**: `staff_schedules` から「その時間に出勤している人数」を
  容量にする案。魅力的だが、受付だけの人・ベッド数がボトルネックの店で外れる。
  店が明示的に決めるほうが確実
