# スタッフ別の受付可否（シフト）（2026-08-20）

エアリザーブの「リソース（スタッフ）ごとの受付時間」に当たる。

## 何が無かったか

担当スタッフの指名（`bookings.staff_user_id`、2026-08-04）は入っているのに、
**「そのスタッフがいつ働いているか」という概念がどこにも無かった。**

火・木しか出ていないトレーナーでも、月曜の枠に指名予約が入ってしまう。
指名を実際に使い始めた店が必ず踏む穴。

## 🔴 行が1件も無いスタッフは「営業時間どおり」

**これが最重要の後方互換ルール。**

既存のスタッフには当然1行も無いので、「行が無い＝働けない」と解釈すると
**適用した瞬間に全店の指名予約が取れなくなる**。

| そのスタッフの行 | 解釈 |
|---|---|
| 0件 | 営業時間どおり（＝シフト未設定。従来の挙動） |
| 1件以上 | **書いてある曜日だけ**働く。書いていない曜日は休み |

「シフトを設定する」＝「働く曜日を列挙する」。全部消せば未設定に戻る。
設定画面も「全部OFFにして保存」＝行0件＝解除、で通している
（「全曜日休み」は表現しない。それをやりたいならスタッフから外すのが筋）。

この規則は **クライアント（`src/lib/staffSchedule.ts`）と DB トリガー
（`guard_booking_staff_shift`）の両方に同じ形で書いてある**。
`src/test/staffSchedule.test.ts` が両者の一致を見張る。

## 店の営業時間との関係は「積集合」

スタッフが 8:00-23:00 と書いても、店が 10:00-21:00 なら 10:00-21:00 でしか取れない。
逆に店が開いていてもスタッフが休みなら取れない。**両方を満たす時間だけ**が枠になる。
定休日（店が閉まっている日）はスタッフの行に関係なく取れない。

## SQLSTATE を分ける

| コード | 意味 | お客様への案内 |
|---|---|---|
| `GB001` | その担当が同じ時間帯に別の予約を持っている | **別の時間**なら取れる |
| `GB002` | その担当はその曜日・時刻に働いていない | **別の担当か別の曜日**なら取れる |

案内が変わるので混ぜない。文言一致で判定しないのは、業種フォークが
メッセージを言い換えた瞬間に静かに壊れるため（2026-08-04 と同じ理由）。

## なぜ `check_booking_overlap` を書き換えなかったか

あの関数は `bookings` と `trial_bookings` の**両方**に付いていて、
`trial_bookings` には `staff_user_id` が無いため `to_jsonb(NEW) ->> …` で読んでいる。
満枠判定という主目的に別の理由を混ぜると、どちらが原因で落ちたのか
エラーメッセージから分からなくなる。**専用のトリガーを別に足した**
（`guard_booking_staff_assignment` が既に同じ形で並んでいる）。

## 🔴 曜日は JST の暦日で数える

```sql
v_jst := (NEW.booking_date AT TIME ZONE 'Asia/Tokyo');
v_dow := EXTRACT(DOW FROM v_jst)::int;
```

`booking_date` は timestamptz なので、そのまま `extract(dow)` すると
**UTC の曜日**になり、23:00 の予約が前日扱いになる。

## テーブル

```
staff_schedules(id, tenant_id, user_id, weekday 0-6, start_time "HH:MM", end_time "HH:MM", …)
  UNIQUE (tenant_id, user_id, weekday)   -- 1人1曜日1行（分割シフトは持たない）
  CHECK  (end_time > start_time)
```

- 時刻を `text` で持つのは `operating_hours` と同じ表現に揃えるため
  （`time` 型だと `"10:00:00"` になり、クライアント側で毎回削ることになる）
- RESTRICTIVE の `tenant_isolation` ＋ 読みは同ジムのメンバー、書きは owner/trainer のみ
- **anon には一切見せない**（公開ページに担当の指名は無い）
- `delete_my_gym` に `DELETE FROM public.staff_schedules` を追加済み

## 画面

- 設定 → 「スタッフのシフト」（`TrainerStaffSchedule.tsx`）
  **スタッフが2人以上いるジムでだけ出る**（1人ジムには指名の概念が無い）
- 保存は「そのスタッフのぶんを丸ごと消して入れ直す」。曜日ごとの差分を取るより
  状態がずれない（UNIQUE 制約とも喧嘩しない）
- 予約側は、指名した担当が出勤していない曜日をカレンダーで選べなくする。
  担当を選び直したときに選択中の日が休みなら、**日付ごと外す**
  （残すと「日付は選ばれているのに枠が0件」になり、空きが無いのか休みなのか分からない）

## 終了に `"24:00"` を許す（2026-08-21 に是正）

営業時間の選択肢を1日の全域に広げたとき（「選べる時間の範囲が狭い」という
実店舗からの指摘）、**シフトだけ 23:30 のまま取り残されていた。**

| | 開始 | 終了 |
|---|---|---|
| 営業時間 | 00:00〜23:30 | 00:30〜**24:00** |
| シフト（是正前） | 00:00〜23:30 | 00:00〜**23:30** ← 狭い |
| シフト（是正後） | 00:00〜23:30 | 00:30〜**24:00** |

24時間営業の店で「20:00〜24:00 のスタッフ」が表現できず 23:30 で切るしかなかった。
**営業時間で選べる終業がシフトで選べない**のは単純な不整合。

- DB の CHECK を `'^(([01][0-9]|2[0-3]):[0-5][0-9]|24:00)$'` に広げた
  （`20260821010000_staff_schedules_end_of_day.sql`）
- **開始側は広げない。** `"24:00"` は終端専用の値で、24:00 に出勤を始める人は居ない
- `staff_schedules_range CHECK (end_time > start_time)` はそのまま効く。
  ゼロ埋めの `"HH:MM"` なので辞書順＝時刻順で、`"24:00" > "23:30"` は true
- **トリガーは直していない。** `guard_booking_staff_shift` は `split_part` で分に
  直しているので `"24:00"` → 1440 でそのまま正しく動く
