# お知らせの画像（2026-11-01）

## 要望

宗本さん（「新規お知らせ」の画面のスクリーンショットを付けて）:

> お知らせで画像を送れる様にして

## 決めたこと（既定の判断）

- 1つのお知らせに**4枚まで**。JPEG・PNG・WebP（スマホの写真は画面で長い辺 1600px の JPEG に描き直してから上げる）。
  1枚 5MB まで（置き場の上限。描き直したあとなら普通は数百 KB）
- 画面: 「本文」と「アイコン」の間に「画像」。選ぶとその場で上げて小さく並べる。×で外せる。選んだ順に並ぶ
- お客様の画面: 本文の下に横幅いっぱいで並べる。押すと全画面（チャットの添付と同じ `ImageLightbox`）
- 店側の一覧に「画像N枚」、お客様の一覧に画像の印

## 🔴 置き場は非公開（URL を知っていても、届いていない人には見えない）

バケット `announcement-images`（非公開）。パスは `<tenant_id>/<uuid>.jpg`。
`supabase/migrations/20261101130000_announcement_images.sql`

| | 誰が |
|---|---|
| 読む | そのジムのスタッフ（オーナー・インストラクター）と、**その画像が付いたお知らせを読める人** |
| 上げる・消す | お知らせを作れる人＝オーナー（インストラクター＝制限付きスタッフは不可。お知らせの書き込みと同じ） |
| 上書き | だれも（UPDATE のポリシーを作っていない） |

- 「読める人」は `announcements` の読み取り権限（RLS）を**そのまま**使う（`EXISTS (SELECT … FROM announcements …)`）。
  「個別」「全員から除く」で外れた人・予約公開の前のお客様・退会した人・他のジムの人・未ログインには見えない。
  配信対象の決まりを置き場の側に書き直していないので、`announcement-audience.md` の決まりが変わっても揃ったまま
- 画面は**署名つきの URL（1時間）**で表示する。公開 URL（`getPublicUrl`）は使わない
- 公開のバケットにしなかった理由: URL を知っていれば誰でも見られる（お客様の写真を載せることもありうる）

## お知らせの行

- `announcements.image_paths text[]`（既定 `'{}'`）。CHECK `announcements_image_paths_shape`
  （`_announcement_image_paths_ok`: 4枚まで・**そのお知らせのジムのフォルダ**の `<uuid>.jpg|png|webp` だけ）。
  他のジムの画像のパスを書いて、他のジムの画像を見せる、はできない
- 保存は今まで通り `save_announcement`（SECURITY INVOKER）に `p_image_paths` を足した。
  🔴 **`p_image_paths` が NULL（送らない）なら画像は変えない。** 古いアプリから保存しても画像が消えない。
  新しい画面は毎回すべて送る（空の配列＝画像なし）
- 引数を足したので、古い7引数の関数は消した（同じ名前が2つあると、古いアプリの呼び出しがどちらか決められずに落ちる）
- 以前からあった `image_url` / `image_url2` は**使わない**（CHECK `announcements_legacy_image_urls_unused` で常に NULL）。
  画面が URL をそのまま `<img>` に入れていたので、外のサイトの画像だと**見た人の IP アドレスがそのサイトに渡る**。
  値の入った行は0件だった（2026-11-01）
- `_announcement_image_paths_ok` は未ログインでも呼べる（関数を作ると既定でそうなる）が、
  表を読まない文字列の検査だけなので害は無い（点検で挙がったらこれを読ませる）

## 片付け（置き場にごみを残さない。残っても、ジムのスタッフ以外には見えない）

- 保存せずに閉じた → そのフォームで上げた画像を消す
- 上げたばかりの画像を×で外した → すぐ消す
- 保存済みの画像を×で外した → **保存できてから**消す（保存しなかったら消さない。配信済みのお知らせから画像が消えないように）
- お知らせを消した → 付いていた画像も消す（本当に行が消えたときだけ）
- 閉じたあとに上がり終わった画像 → 次に開いたフォームに混ぜずに消す（フォームの番号で見分ける）
- ⚠️ ジムを閉じた（`delete_my_gym`）ときの画像は残る（SQL から置き場は消せない＝`storage.protect_delete`）。
  読めるのはそのジムのスタッフだけで、閉じたあとはスタッフもいないので誰にも見えない

## ジムの決め方

画面は `useTenant().tenant.id` のフォルダに上げ、お知らせのジムは DB の `get_my_tenant_id()` で決まる。
どちらも「在籍している所属の1件目」なので普通は同じ。もし食い違ったら CHECK で保存が断られる（漏れる方向には壊れない）。
2026-11-01 時点で、複数のジムに在籍しているスタッフは0人。

## 古いアプリ

- 画像は出ない（題名・本文は今まで通り）。次のネイティブのビルドから出る。Web は Publish で出る
- 古い店側の画面で保存・編集しても画像は消えない（上の 🔴）。古い画面は直接 `announcements` に書く場合もあるが、
  `image_paths` に触らないので同じ

## 本番への適用（2026-11-01）

1. 試しに流して取り消す: 上げる（オーナーだけ・自分のジムのフォルダだけ・決まった形だけ。インストラクター・お客様・
   他のジムのオーナー・未ログインは断られる）／保存（形の検査・5枚・他のジムのパス・NULL の要素・`image_url` は断られる。
   インストラクター・お客様は保存できない）／読む（全員向け＝読める、予約公開の前＝読めない、個別＝選ばれた人だけ、
   除く＝除かれた人は読めない、退会した人・他のジム・未ログインは読めない、スタッフは全部読める）／
   古い呼び方で画像が残る・空の配列で外れる／消すのはオーナーだけ／上書きはだれもできない／
   画面が読むもの（お知らせ・既読・名簿・予約・置き場全体の件数）が前後で同じ — すべて期待どおり
2. 同じ確認を期待値と突き合わせながら適用（埋め込んだ SQL の md5 を確かめてから）
3. 適用後に別の取引で演じ直し: お客様のお知らせの件数が変わらない／オーナーが画像付きで保存したお知らせの画像を、
   届いたお客様が読める（取り消し済み）

## 2026-11-02: 画像だけでも送れる（タイトル・本文は空でよい）

宗本さん「お知らせ、タイトルと文章入れなくても画像だけでもお知らせ送れる様にして」（チラシを1枚送りたい）。

- **画像が1枚以上あれば、タイトルと本文は空でよい**（どちらか一方だけでも可）。
  画像が無いときは、今までどおりタイトルと本文の両方が要る（エラー文は「タイトルと本文を入力するか、画像を付けてください」）
- **タイトルが空なら「画像のお知らせ」を入れて保存する**（`announcement.imageOnlyTitle`。店の画面の言葉で入る）。
  - お客様の一覧・プッシュ通知の見出し（「お知らせ: 画像のお知らせ」）が空にならない
  - 画像を出せない古いアプリ（次のネイティブビルドより前）でも、空の行にならない（画像は見えない）
  - プッシュの本文は空なので、送信側の既定「新しい通知があります」になる（`send-push-notification`。関数は変えていない）
- 本文が空のお知らせは、お客様の詳細・店の一覧で本文の欄を出さない
- 画像を上げている途中は、今までどおり保存させない（画像だけのお知らせだと空のまま配信されるため、先に判定する）
- DB（`save_announcement`・表）はもともとタイトル・本文の空を断っていない（NOT NULL だけ）ので、変更なし
