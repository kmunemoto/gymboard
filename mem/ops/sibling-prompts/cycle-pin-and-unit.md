# 「起算日の固定」と「利用期間の単位」を実装し、月末バグを点検してください

ジムボード（このアプリの元）で 2026-08-22 に実装・本番稼働済み。3点セットです。
決定事項は変えず、名前・文言はこのアプリの現物に合わせてください。
**前提**: プラン回数上限の強制（allow_overflow・契約ガード・窓の SQL 関数）が
実装済みであること。未実装ならそちらを先に。

## 1. 起算日の固定（店の設定が最上位）

お客様の利用期間には自動ルールがある（1回目の予約日への合わせ込み・使い切り後の
ロール・1回目起点の引き直し表示——このアプリの courseProgress 相当を確認）。
店が手で入れた起算日をこの自動ルールが動かしてしまうので、**店の設定を最上位にする
明示スイッチ**を足す。

- `profiles.cycle_start_pinned BOOLEAN NOT NULL DEFAULT false`。
  カルテの起算日入力の下に「起算日を固定（自動調整しない）」スイッチ。
  🔴 **暗黙に固定しない**（店が日付を手入力しただけでは固定にしない。既存の運用を
  黙って変えると自動ルール前提の他店の挙動が変わる）
- 固定中のお客様:
  - 起算日の自動書き換え（予約時のリベース）… **一切しない**。
    例外は起算日 NULL からの初回設定だけ（UI は日付なしでは ON にできない）
  - 使い切りロール・1回目起点の引き直し表示 … しない ＝ **起算日から暦どおりに
    進む純粋な窓**（DB の窓関数と表示が完全に一致する）
  - 期限の「1回目の予約待ち（未確定）」表示 … 出さない（期間は店の設定で確定済み）。
    期限リマインドの Edge Function 側も同じ判定にする
  - 契約ガード（前提プロンプトの GB005 相当）に2規則を追記:
    **本人はスイッチを変更不可**・**固定中は起算日も本人変更不可**
    （allow_overflow=true のプランでは従来本人が書き換えられた穴を塞ぐ）
- UI: 日付なしではスイッチ無効。日付を消したら固定も自動解除

## 2. 利用期間の単位（ヶ月／週／日）

利用期間が「Nヶ月」しか選べないのを、店ごとに ヶ月/週/日 から選べるようにする。

- `tenant_plans.cycle_unit TEXT CHECK (IN ('months','weeks','days'))`、NULL=months。
  既存の月数列（cycle_months 相当）は「**単位数**」として使い回す（列は増やさない）
- 🔴 **規則は非対称（互換のため）**:
  - **months** … 従来どおり**応当日ベース・応当日を含む**（6/5開始→7/5まで、翌サイクルは
    7/6 から）。既存プランの窓を1日も変えないため、この規則は**変更しない**
  - **weeks / days** … **ちょうど N×7日 / N日** の連続窓 `[start, start+span)`。
    翌サイクルは end 当日から（応当日の概念が無いので最終日を共有しない）
- DB は窓関数に**単位付きのオーバーロード**を追加（months は既存版へ委譲・週日は
  整数除算の直接計算）。上限強制トリガーが単位を読んで窓を引く
- クライアントは窓計算の全経路（表示・リベース判定・進捗チップ・期限リマインドの
  Deno 移植）に単位を配線する。単位のリゾルバ（プラン名→unit）を1本作る
- ⚠️ **公開済みの旧アプリは単位を知らない**。週・日のプランを「Nヶ月」と誤表示する
  （DB の強制とサーバー通知は正しい）。単位を月以外にする店には新ビルド配布後に案内

## 3. 🔴 月末クランプの点検（既存バグの可能性が高い）

期限リマインドの Edge Function が使う**サイクル計算の Deno 移植**
（`supabase/functions/_shared/cycle.ts` 相当）があるなら、**月の加算が月末を
クランプしているか**を必ず確認する。ジムボードでは
`Date.UTC(y, m+1, day)` 方式で **1/31+1ヶ月 → 3/3** になっており（クライアントの
date-fns と DB の Postgres interval は両方 2/28 へクランプ）、**月末起算
（29〜31日）のお客様だけリマインドの窓が表示とずれていた**。繰り上がりの累積で
丸ごと1サイクルずれるケースもあった。対象月の末日で丸める実装に直す:

```ts
const lastDay = new Date(Date.UTC(y, mo + 1, 0)).getUTCDate();
return Date.UTC(y, mo, Math.min(day, lastDay));
```

クライアント↔Deno 移植のパリティテストに**月末アンカーのシナリオ**
（1/31・8/31・数サイクル後・閏年 2024-01-31）を足す。修正前の実装で赤になることを
確認してから直す（ジムボードでは4本とも赤だった）。

## 検証

- 変異検証: 固定のゲート（リベース・ロール・引き直し・periodPending）各所／
  週の span（×7）／床関数→天井／契約ガードの2規則——を壊して赤を確認
- 本番3段構え: 適用 → 会員を演じて「固定中の起算日変更・スイッチ変更→拒否」、
  店を演じて「固定中でも変更可」、NULL→初回設定は固定でも通る、窓関数の単位別の
  境界値（週の end 当日・月の応当日・閏年）——すべて BEGIN…ROLLBACK
- migration はマージ直前に本番へ適用。期限リマインドの Edge Function は
  マージ後に Lovable へデプロイ依頼（秘密情報を書かない）→ 非404 確認
- ゲートグリーン → PR → マージ
