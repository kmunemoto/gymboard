# 予約のオプション（booking_options）

**2026-09-02 開始。いまは「店が設定できる」ところまで。**

## 何のためのものか

実店舗の要望（宗本さん）:

> 私のジムはオプションにトレーニング後に30分3000円のストレッチのプランも加えます。
> 予約する時にストレッチを付けるか選べるようにしたいと考えています。
> …トレーニング時間とストレッチの間にもちろん15分は開けません。
> **一つのセッションの時間として扱います。**

## 🔴 占有時間の規則（ここだけは間違えない）

```
1枠60分 ＋ オプション30分 ＋ 次のお客様までの間15分 ＝ 105分
```

**「60 + 15 + 30 + 15 = 120」ではない。** 間（`tenants.booking_buffer_minutes`）は
**1回だけ**。トレーニングとストレッチの間には入れない。

2回取ると、実際には空いている15分が予定表から消える。**これは例外を出さない。**
夜の枠が1つ減るだけで、気づけるのは「なぜか予約が取れない」と言われたとき。

計算は `src/lib/bookingOptions.ts` の `sessionFootprintMinutes` 1本に寄せてある。

お客様に見せる「セッションの長さ」は `sessionMinutes`（1枠＋オプション、**間は含めない**）。
間は店の都合の時間で、お客様の時間ではない。`09:00〜10:30` の表示に混ぜてはいけない。

## 第1段（PR #367）でできたこと

- 店が `booking_options` を作れる（名前 / 追加時間 / 料金 / 受付中・停止中 / 並び順）

### 画面側で直した場所

- `parseBooking`（`useBookings.ts`）に足したことで、**8つの表示が一度に直る**
  （お客様の予約一覧・ホームの次回予約・履歴・店の予定表の週/日・週タイムラインの
  ブロックの高さ・カルテ・キャンセル確認・Googleカレンダーのリンク）
- `parseBooking` を通らない**独自の写し**が2つあるので個別に直した:
  `TrainerClientDetail.tsx`（カルテの予約一覧）と、予約直後の確認ダイアログ
- お客様の予約画面: 空き枠・終業前の打ち切り・「09:00〜10:30（90分）」の3つ
- 店側の代理予約（`TrainerSchedule`）にも同じ選択欄を出した。
  出さないと**店から入れた予約だけ占有が短くなる**
- Edge Function 3本（Deno なので `src/` を import できず、写し忘れが起きる場所）:
  `notify-new-booking`（新規予約のメール・プッシュ）/ `calendar-feed`（お客様のICS購読）/
  `google-calendar-sync`（トレーナーのGoogleカレンダー）

### 🔴 オプションを選び直したら、選択中の枠を必ず外す

占有が伸びる＝選べる枠が変わる。外さないと「画面では選べているのに送信すると
DB に断られる」になる。`useBookingOptionSelection({ onChange })` がその口。
選択欄は**時間を選ぶ前**に置いてある。

実測（fixtures モード、終業21:00・1枠60分）:
ストレッチ（+30分）を付けると最終開始が **20:00 → 19:30** に縮み、
確認欄が **09:00〜10:30（90分）** になる。

### 予約変更（リスケ）の扱い

- 変更中はオプションを**選び直させない**（事前アンケートと同じ）。元の予約のぶんを引き継ぐ
- 引き継ぎは `createBooking` の3箇所すべてに渡す（**失敗時の復元も含む**）。
  リスケは「旧行を削除 → 新行を INSERT」なので、渡さなかった列は消える
- 空き枠の判定にも**元の予約の分数**を使う。0 にすると必ず DB に拒否される

### ついでに直した既存の不具合

`TrainerDashboard` の今日の予定が **「60分」の直書き**だった。50分・90分で回している
店では、オプション以前から嘘の表示になっていた。予約行の実際の長さを出すようにし、
`dashboard.minutes60` は5言語とも削除した。

### ② あとから店側でオプションを足せる（🔴 GB008）

> あとからオプション追加したいっていう人もいるかもなので追加して。
> でもそれはお店側で追加する。**後ろがもう埋まってたら無理だしね**

予定表で予約をタップ →「オプションを変更」。

**「後ろが埋まってたら無理」を成立させるために、専用のトリガーを新設した**
（`guard_booking_option_change` / `20260904000000`）。ここが第3段の本体。

重複判定（`check_booking_overlap`）は **BEFORE INSERT にしか刺さっていない**
（日時変更が「作ってから消す」で実現されているため。20260804000000 の方針）。
つまり「あとから足す」＝ UPDATE で占有だけ伸ばす操作は、**何の検査も通らない**。
60分の予約に30分足すと予定表の上で黙って105分に伸び、**すでに入っている次の
お客様の枠を飲み込む**。画面には2件が重なって表示され、当日まで誰も気づかない。

🔴 **このガードは bookings の BEFORE UPDATE に刺さる＝キャンセル・消化・メモ追記・
担当変更の「すべての UPDATE」がここを通る。** 先頭の
「増えていないなら即 RETURN」を消すと、**予約のキャンセルまで巻き添えで落ちる**。

判定は `check_booking_overlap` と同じ形（自分以外の予約・体験・ブロック枠を数え、
時間帯の帯 → 店の既定値の同時受け入れ数と比べる。担当の重なりも見る）。
**短くする方向は素通し**（占有が縮むので誰ともぶつからない）。

- SQLSTATE は **GB008**（この用途専用）。満枠の文言と混ぜない——店員への案内が
  「別の時間なら取れる」ではなく「この予約は伸ばせない」で、対処が違う
- 画面側は**先回りして判定しない**。持っている予約一覧はその日ぶんだけで、
  帯もブロック枠も含んだ正しい判定は DB にしか無い
- **お客様側からは変更できない。** 伸ばせるかは「後ろの予約」次第で、それは
  お客様には見えない（誰の予約かは出さない）。断られる理由を説明できない操作は出さない
- 長さが変わるので Google カレンダーは**消してから作り直す**
  （`google-calendar-sync` に「長さだけ変える」経路が無い）

### ④ 変えたらお客様に知らせる（PR #371）

> 通知を足して

店側からの操作なので、黙って変えると**お客様は終了時刻が変わったことを知らない**。
逆に「勝手に付けられた」とも見える。**プッシュ＋メールの2本**で知らせる
（キャンセル通知と同じ形）。

🔴 **プッシュだけにしない。** 許可していないお客様には何も届かないので、
メールが唯一の控えになる。

送らない場合が2つある:

- **中身が変わっていないとき**（同じものを選び直して保存しただけ）
- **過ぎた予約**（記録の手直しであって、お客様への連絡ではない）

同じ内容を2回押しても2通にならないよう、`option-change-<予約id>-<分数>-<オプションid>`
を冪等キーにしている。分数と中身の両方を鍵に入れているので、**外して付け直したときは
ちゃんともう1通出る**。

知らせる時間帯は**変更後**のもの（1枠＋オプション。間は入れない）。

- テンプレート: `supabase/functions/_shared/transactional-email-templates/booking-option-changed.tsx`
- 外したときは「オプションはございません」ではなく**「取り消しました」**と書く
  （何も出ないと、何が起きたのか分からない）
- `CLIENT_ALLOWED_TEMPLATES` に足した。宛先は `_resolve_user_` 経路なので
  「**自分がスタッフをしているジムの在籍者**」にしか届かない（宛先の自由入力にならない）。
  見張り: `src/test/transactionalEmailTenantScope.test.ts`

🔴 **文言はコードに直接書いている（i18n を通していない）。** この層——通知の送信——は

i18n にすると「どこで訳すのか」が2通りになる。多言語にするなら通知層をまとめて変えること。

## 設計の判断

**なぜ `tenant_plans` と別の表か。** `tenant_plans` は「どのコースを契約しているか」で、
回数・料金・消化の対象。オプションは1回の予約に後付けする追加で、契約とは別物。
混ぜると「プラン一覧」に 30分ストレッチが並び、回数の消化や請求の対象に見える。

**料金は表示のための数字。** ジムボードはアプリ内で施術料の決済をしない
（Stripe はサブスク課金のみ）。`price_yen` はお客様に見せる金額で、支払いは店頭。
**0 は「無料」ではなく「料金を表示しない」**（掲示したくない店・回数券に含む店がある）。

**追加時間 0 分を許してある。** プロテイン・レンタルウェアのような「時間は増えないが
料金は付く」オプションのため。

**保存しても id を変えない。** `TrainerCapacityWindows` は「全挿入 → 差分削除」で
毎回 id が変わるが、オプションは将来 `bookings` 側から id で指す（何を付けたかを
残す）ので、差し替えると過去の予約から辿れなくなる。既存行は `update` する。

## 🔴 出荷した不具合: 追加した1件が保存直後に消える（2026-09-03 に発覚・修正）

第1段（#367）から入っていた。**設定画面でオプションを追加して保存すると、
「オプションを保存しました」と出るのに一覧が空のまま**になる。
本番の `booking_options` を数えたら**全テナントで0件**だった。
つまり誰も1件も設定できていなかった＝機能はまるごと動いていなかった。

行が入っていなかったのではない。**入ったあと、同じ保存の中で自分で消していた。**

```ts
// 出荷してしまった版
const { error } = await supabase.from("booking_options").insert(added as never);
//                                                       ↑ .select("id") が無い

const keepIds = rows.map((r) => r.id).filter(Boolean);   // 画面のローカルな id だけ
const del = supabase.from("booking_options").delete().eq("tenant_id", tenant.id);
const { error: delErr } = keepIds.length > 0
  ? await del.not("id", "in", `(${keepIds.join(",")})`)
  : await del;                                            // ← 条件なしの全削除
```

1. 追加した行は id が `null`。insert で採番された id を受け取っていなかった
2. 「残す id」は画面にもとから在った行の id だけ。**初回の追加では空配列**になる
3. 空配列 → 条件なしの全削除に落ちて、いま入れた行ごと消える
4. トーストは DB の結果ではなく `options.length`（画面の状態）を見るので成功に見える

### なぜ見張りをすり抜けたか

`bookingOptions.test.ts` には
「🔴 削除は最後（追加が失敗したときにオプションが静かに消えないため）」があった。
だがこれは `indexOf` で **update / insert / delete の順番**を見ていただけで、
**削除の条件が正しいか**は1つも見ていない。順番は正しく、条件が間違っていた。

本文の検査（このファイルにこの文字列が在るか）は「書き忘れ」には効くが、
「書いてあるが間違っている」には効かない。**保存のように結果が消えるものは、
実際に走らせて残るかどうかを見ないと分からない。**

### 直したかたち

- `insert(...).select("id")` で採番された id を受け取り、「残す id」に足す
- **条件なしの全削除は「画面が0件のとき」だけ**（`rows.length === 0`）。
  残す id の件数で判断しない
- 万一 insert が id を返さなかったら削除を見送る。
  消し損ねは次の保存でやり直せるが、全削除は取り返せない

`src/test/trainerBookingOptionsSave.test.tsx`（9件）を追加した。
偽の DB（PostgREST の使っている範囲だけを真似た `select/insert/update/delete/eq/not/order`）
を相手に、実際に画面を操作して保存を走らせ、行が生き残るかを見る。
出荷した版のコードに戻すと3件落ちることを確認した。

変異5種すべてで赤くなる:

| 変異 | 落ちる件数 |
|---|---|
| 出荷した元のコードそのまま | 3 |
| `insert` から `.select("id")` を外す | 2 |
| 全削除の条件を「残す id の件数」にする | 1 |
| 絞り込み削除から `tenant_id` を外す | 1 |
| 既存行の更新を飛ばす | 1 |

### 持ち帰り

- **書き込みの検査を本文の検査で済ませない。** 順番・存在の確認は条件の誤りを捕まえない
- **成功のトーストを画面の状態から出さない。** DB の結果から出す
  （今回は各段が error で早期 return するので直った後は一致するが、
  「成功に見える」が発覚を遅らせた）
- 同じ形の兄弟に `TrainerCapacityWindows` がある。そちらは
  `insert(...).select("id")` → `keepIds` → `.not(...)` と正しく書けていた。
  **写すときは削除の条件まで写す**
