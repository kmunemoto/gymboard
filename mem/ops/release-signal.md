# 全兄弟アプリへ: 「リリースノート書いて」＝ リリース完了の合図

2026-08-05 に宗本さんが決めた取り決めです。**全アプリ共通。**

---

## 取り決め

> 僕がリリースノート書いてと言ったら、もうそこまでのバージョンはリリースしたんだな、と
> 理解してください。**わざわざリリースし終わったことを報告しないので。**

**これがリリース完了を知る唯一の信号です。** 他に通知は来ません。

---

## なぜこれが要るのか

ストアへの提出は宗本さんが手で行います。**セッションからは確認する手段がありません。**

- iOS … Actions はアップロードまで。審査・公開は人の操作
- Android … Windows + Android Studio で署名 → Play Console へ手でアップロード
- **`android/` は `.gitignore` 済み**なので、実際に出た版数はリポジトリから読めない
- クラウドセッションからは Play Console も App Store Connect も見られない

上流では実際に、**`versionCode` の現在値が分からず版を上げようがない**という事故が
起きた。毎回「リリースしましたか？」と聞くのは宗本さんの手間が増えるだけなので、
**依頼そのものを信号にする**ことで確認のやり取りを無くす。

---

## 言われたらやること

`リリースノート書いて` と言われたら、**文章を書く前に**版数を進める。

```
1. リリース実績の記録に、いま出ていた版を実績として書く
2. iOS 側のバージョン表記（ios-build.yml の MARKETING_VERSION）を更新する
3. そのうえで新しい版のリリースノートを書く
```

🔴 **ジムボードでは Android の版数は上げない**（2026-08-13 から）。
リポジトリに版数を持っていないので、`android/app/build.gradle` を Android Studio で
直接上げる＝宗本さんの手元の作業になる。**セッションからは現在値も読めない。**
下の「版数の現在値を、リポジトリに持っているか」を参照。

**「リリースしましたか？」と聞き返さない。** 聞かなくても分かるようにこの取り決めがある。

### 版を上げるか迷ったとき

**同じ版のノートを直したいだけ**の依頼もある（内容の追記・訂正など）。
直前のやり取りが同じ版についてなら、版は上げない。

判断がつかないときは **上げる方を選ぶ。**

| | 起きること |
|---|---|
| 余分に上げた | `versionCode` が1つ飛ぶだけ。**害はない**（単調増加でありさえすればよい） |
| 上げ足りなかった | Play が `Version code N has already been used` で弾く。**ビルドし直し** |

---

## 版数の現在値を、リポジトリに持っているか

この取り決めが機能する前提として、**「次に出す版数」がリポジトリから読める**必要がある。

### 🔴 ジムボードは一度これをやって、2026-08-13 にやめた

2026-08-05 に `android-version.json`（＋ `set-android-version.mjs` ＋ テスト17件、PR #268）を
作った。それ以前は `android/app/build.gradle`（`.gitignore` 済み）を手で書き換えていたため、
**現在値がどこからも読めなかった**からだ。

**やめた理由: Play の実態と同期しない記録は、正しく見えるぶんかえって危ない。**

実際に起きたこと。8/11 に `android-version.json` を 86/9.5 へ進めたが、Play への
アップロードは結局しなかった。**リポジトリだけが「9.5 を出した」ように見える状態が
2日続いた**（リリース実績表にも「Play へ上げたかは未確認」の行が 85 と 86 の2つ残っている）。
版数を Android Studio で直接持てば、**唯一の記録は Play Console だけ**になり、二重管理が消える。

削除したもの: `android-version.json` / `scripts/set-android-version.mjs` /
`src/test/androidVersion.test.ts`、および `build-android.bat` の呼び出し。

**代わりに失ったもの（受け入れたうえで削除している）:**

- 「バージョンを1つ上げて」に応えられない。値は宗本さんの Windows にしか無い。
  **推測で書かないこと**
- 「版を上げた」がコミット履歴に残らない
- `npx cap add android` で作り直すと Capacitor 既定値（`versionCode 1` / `"1.0"`）に戻る

緩和として、`build-android.bat` が最後に `build.gradle` の現在値を**表示する**
（書き換えはしない）。1 に戻っていればその場で気づける。

### 兄弟アプリはどうするか

**どちらでもよいが、二重管理にはしないこと。** 正が2つあると必ずずれる。

- **手作業でリリースするアプリ** … ジムボードと同じで、Play Console を唯一の正にするのが素直。
  「リポジトリからは読めない」を受け入れる
- **CI でリリースするアプリ**（ストレッチボード等） … `versionCode` は
  `BASE(10000) + run_number` で自動導出されるので**そもそもずれない**。
  この場合はリポジトリに持つのが正しい（`versionName` だけは手で持つ必要がある）

### CI を使っているアプリは採番の線に注意

このリポジトリは手作業側が 82 から1ずつ、Android CI を使うアプリ（ストレッチボード等）は
`BASE(10000) + run_number` のように、**ぶつからない採番にする**（テストで見張る）。

このリポジトリの `android-build.yml` は作ってあるが CI 経路としては使っていない
（手作業のまま）。CI 経路のアプリでは `versionCode` が `github.run_number` から
自動導出され、手作業のような「上げ忘れ」自体が構造的に起きない。その場合でも
`versionName` は自動で決まらず入力が必要になるので、そちらは**別途トラッキングする値**
として repo に持つこと（詳細は各アプリの `mem/features/android-ci.md` 相当）。

---

## それでもストアが正である

この取り決めは「聞かなくて済む」ようにするもので、**実態と自動同期はしない。**

記録の取りこぼしや依頼の行き違いはありえる。
**アップロード直前に Play Console / App Store Connect の最新版数を必ず確認すること。**

ジムボードはリポジトリに版数を持っていないので、**Play Console を見る以外に確かめようがない。**
`build-android.bat` が表示するのは手元の `build.gradle` の値であって、
**Play に上がっている値ではない**（この2つがずれているのが、まさに事故の形）。

---

## まとめ

```
「リリースノート書いて」
  → 前の版はもう出ている
  → 実績を記録し、版数を1つ進めてから、ノートを書く
  → 「リリースしましたか？」とは聞かない

迷ったら版は上げる（飛ぶのは無害・足りないのは弾かれる）
アップロード前にストアの実物を確認する
```
