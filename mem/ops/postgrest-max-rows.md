# 1000件の壁（PostgREST の max-rows）

**Supabase（PostgREST）は1回の問い合わせで最大1000行しか返さない。超えた分はエラーにならず、黙って欠ける。**
古い順に並べて読んでいると、欠けるのは**いちばん新しい行**（これからの予約・最近の記録）なので、
画面からは「最近の分だけ無い」ように見え、気づきにくい。

2026-11-02 に宗本さん「予定表の1000件の件も直して」で、ジム全体・全期間を読むところを直した。

## 決まりごと

1. **全件が要る読み込みは `fetchAllRows`（`src/lib/fetchAllRows.ts`）を通す。** 1000行ずつページに分けて最後まで読む。
   - サーバー側（Edge Function）は Deno なので同じものを各関数に持つ（例: `push-period-reminder` の `fetchAllRows`）
2. 🔴 **ページで読むときは、並びの最後に一意の列（`id`）を足す。**
   - 日付だけで並べると、同じ日付の行がページの境目をまたいだとき、問い合わせごとに並びが変わる。
     そのため、同じ行が2回出たり、1行抜けたりする。
   - 2026-11-02 に本番の DB で再現した。トレーニング記録（いちばん多いジムで2,488件。同じ日付が207日ぶん）を、
     CSV 書き出しと同じく日付だけで1000件ずつ読むと、**4件重複・4件欠落**した。`id` を足すと0件。
3. **件数は `select("id", { count: "exact", head: true })` で数える。** 行を読んで `length` を取ると1000で頭打ちになる。
4. 1回に読む行数（1000）は、サーバーの max-rows 以下にする。超えると、上限で切れた短いページを「終わり」と誤解する。

## 要観察（ジムが大きくなったら）

- **空き枠の関数 `get_tenant_booked_slots`**（お客様の予約画面・体験・ドロップイン）
  - 期間つき（今日〜予約できる最終日）だが、関数の戻りも1000行で切れる。
  - 1日20件を超えるジムで、予約できる日数が長いと届く。
  - 届いたら、空いていない枠が空いて見える（DB が二重予約を断るので重なりはしないが、押してから断られる）。
- **Google カレンダーの全同期**（`google-calendar-sync`）
  - これからの予約の全件を読む。1つのジムでこれからの予約が1000件を超えたら、ページ読みが要る。
- **一斉通知の端末一覧**（`send-push-notification` の `push_devices`）
  - お客様数×端末数が1000を超えたら、ページ読みが要る。
