# AIエージェントとの作業の進め方

Claude Code / Grok などでこのリポジトリと兄弟アプリを触るときの取り決め。
**トークンの消費を減らすこと**と、**セッションをまたいでも品質が落ちないこと**が目的。

2026-08-02、ストレッチボードの業種特化作業でプランのトークン上限に達したのを受けて作成。

## 実測: 何がトークンを食うか

上限に達した実際の内訳。推測ではなく計測値。

| 原因 | 実測 | 備考 |
|---|---|---|
| **サブエージェント/ワークフローの並列実行** | **1回で 157万トークン** | 34体を並列で走らせ、20体がレート制限で失敗。成果は部分的にしか得られなかった |
| 会話の長さ | 毎ターン全履歴を再送 | 長い会話の終盤は、1ターンあたりの単価が最初の数倍になる |
| 全文検索の出力 | ヒット数に比例 | `grep -r` が大量にヒットすると、その出力がそのまま課金対象になる |

**桁が違うのはサブエージェントの並列実行**。同じ調査を1体で順にやれば1/10以下で済む。
「速い」の代償がトークンの掛け算であることを、依頼する側が意識する必要がある。

## 取り決め

### 1. 実装作業でサブエージェント/ワークフローを使わない

並列調査は「何がどこにあるか分からない」段階でだけ価値がある。
仕様が決まった実装では要らない。**エージェントに明示的に禁止を伝える**のが確実。

> 例: 「ワークフローとサブエージェントは使わないでください」

### 2. 1タスク = 1セッション

会話は毎ターン全履歴が再送される。設計の議論をした長い会話でそのまま実装に入ると、
実装の各ターンが「議論の全部＋実装」の値段になる。

**タスクが変わったらセッションを切る。** そのために引き継ぎを文書にする（下記）。

### 3. 実装は Sonnet、設計とデバッグだけ Opus

| 作業 | モデル |
|---|---|
| 仕様が決まった実装、i18nを5言語に足す、機械的な置換、パッチ当て | Sonnet |
| 設計判断、原因不明のバグ、コードレビュー、事故の切り分け | Opus |

このリポジトリの作業の大半は前者。`/model claude-sonnet-5` で切り替わる。

### 4. 全文検索より、対象ファイルの直読み

`grep -r` をリポジトリ全体に掛けると出力が膨らむ。
`mem/` の各文書が「どのファイルの何を見ればいいか」を持っているので、
**先に文書を読んで対象を絞り、そのファイルだけ読む**方が安く、かつ正確。

### 5. 検査は段階的に

いきなり `npm test` を全部回さない。
変更したテストファイルだけ → 通ったら全体、の順にする。
全体は 40ファイル以上あり、出力も相応に大きい。

## 引き継ぎ文書の型

セッションを切る前提なので、**次のセッションがコールドスタートで動ける文書**を残す。
これが無いと、新しいセッションが同じ調査をやり直して結局トークンを使う。

含めるもの:

1. **作業リポジトリ**（上流か兄弟アプリか）と、その判断理由
   兄弟アプリの作業は原則すべて上流。`vertical-fork.md` の鉄則2
2. **現状**（実地で確認した行番号・列の有無・grepの結果）。「〜のはず」を書かない
3. **何が問題か**（症状。放置したときに何が起きるか）
4. **やってほしいこと**（ファイルパスつき）
5. **テストの書き方**（下記の作法。ここを省くとフォークでCIが赤くなる）
6. **完了条件**（tsc / test / build / フォーク構成での確認）

**行番号は書く前にその場で取り直すこと。** 直前に merge していると全部ずれている。

## 複数のAIを併用する場合

書き込み権限を持たないAI（2026-08時点の Grok など）を混ぜるときは、
**読む側と書く側で分ける**のが噛み合う。

| 役割 | 担当 | 理由 |
|---|---|---|
| コードベースの調査・仕様出し・レビュー | 読み取り専用のAI | トークンを食うのは読む作業。書き込み権限が要らない |
| 実装・テスト・PR・マージ・フォークへの取り込み | 書き込めるAI | 下記の取り込み手順を知っている必要がある |

逆（読み取り専用のAIに実装させて、差分を人が運ぶ）にすると、
**受け渡しが毎回発生する**うえ、受け取った側が結局は全部検証し直すことになる。

やむを得ず差分を運ぶ場合は、チャットに貼らせず **unified diff をファイルに出力させて添付**する。
マイグレーション＋types.ts＋コンポーネント＋5言語のi18n＋テスト、と範囲が広いと
貼り付けでは取りこぼす。

## このリポジトリ固有の注意（セッションが変わっても引き継ぐこと）

- **上流のテストにブランド値・日本語リテラルを直接書かない。**
  `i18n.t()` と`brand.ts` から引く。既定値そのものの断言は
  `src/test/helpers/upstream.ts` の `upstreamOnly()` で囲う。
  これを守らないと兄弟アプリでCIが恒常的に赤くなる（`vertical-fork.md`）
- **上流で緑でも兄弟アプリで落ちるかは分からない。**
  `brand.ts` / `featureFlags.ts` / `vertical.ja.json` を兄弟の値に一時差し替えして
  `npm test` を回す。この手順で過去に2件見つかっている
- **兄弟アプリへの取り込み後は必ず grep する。**
  Supabase の project ref が5箇所とも自分の値のままか、
  `supabase/config.toml` の `verify_jwt` が Lovable の再生成で消えていないか
- **`-X theirs` を使わない。** 一度これで上流の本番DBを指す状態に戻りかけた
