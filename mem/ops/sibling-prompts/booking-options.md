# 予約のオプション（アドオン）を実装してください

ジムボード（このアプリの元）で 2026-09-02〜09-03 に実装・本番稼働済みの機能です。
決定事項は変えず、テーブル名・SQLSTATE の採番・文言はこのアプリの現物に合わせて
読み替えてください（🔴 SQLSTATE は migrations を grep して**未使用の `GB0xx`** を選ぶ。
ジムボードの番号をそのまま写さない）。

## これは何か

基本の予約枠（1回60分など）に、**追加の時間と料金が乗る任意のメニュー**を選べるようにする。
店が「ストレッチ / +30分 / ¥3,000」のようなオプションを登録しておき、お客様が予約するときに
付けるかどうかを選ぶ。付けるとその予約は長くなり、**予定表をその分だけ余計に占有する**。

## 🔴 いちばん壊れやすいのは占有時間。ここだけは間違えない

```
1枠60分 ＋ オプション30分 ＋ 次のお客様までの間15分 ＝ 105分
```

**「60 + 15 + 30 + 15 = 120」ではない。** 間（buffer）は**最後に1回だけ**。
トレーニングとオプションの間には入れない（実店舗の明言:「トレーニング時間と
ストレッチの間にもちろん15分は開けません。一つのセッションの時間として扱います」）。

間を2回取ると、実際には空いている15分が予定表から消える。**これは例外を出さない。**
夜の枠が1つ減るだけで、気づけるのは「なぜか予約が取れない」と言われたとき。

計算は**関数1本**に寄せること（ジムボードでは `sessionFootprintMinutes(slot, option, buffer)`）。

お客様に見せる「セッションの長さ」は別で、**1枠＋オプションだけ**（間を含めない）。
間は店の都合の時間でお客様の時間ではないので、`09:00〜10:30` の表示に混ぜてはいけない。

## 🔴 占有を計算している場所は5つある。全部そろって初めて正しい

このアプリの現物を grep して、**同じ役割の場所を5つとも見つけてから**着手すること。

| # | 場所 | 忘れるとどうなるか |
|---|---|---|
| 1 | 重複チェック関数（`check_booking_overlap` 相当）の**これから入れる**予約 | 長い予約が入ってしまう |
| 2 | 同・**既存の予約**側 | 🔴 **本物の二重予約**（オプションの最中に次の人が入る） |
| 3 | 同・**体験/ゲスト予約**（別テーブル）側 | ❌ **足さない**。あちらにオプションは無い（列も無い） |
| 4 | 担当スタッフの差し替えガード（`BEFORE UPDATE` で担当の重なりを見るもの） | 「担当を変更」で1人に2件を割り当てられる |
| 5 | 画面が読む「埋まり枠」RPC（`get_tenant_booked_slots` 相当） | 🔴 **空きに見えるのに送信すると断られる**（何度押しても直らない） |

4 は**ジムボードでも最初に見落とした**。トリガーの一覧を機械的に洗い出して確認すること。

## 🔴 `NEW.option_minutes` と直接書いてはいけない

重複チェック関数は **会員予約と体験予約の両方**のトリガーから呼ばれているはず（このアプリの
現物を確認）。体験側のテーブルにこの列は無いので、直接書くと

```
record "new" has no field "option_minutes"
```

で**体験予約の登録だけが実行時に落ちる**。しかもこの文言はお客様には
「サーバーで問題が発生しました」としか出ないので、原因に辿り着けない。

必ず `to_jsonb(NEW) ->> 'option_minutes'` の形で読むこと。

## 段階を分けて出す（各段で出荷できる）

### 第1段: 店が設定できる

- テーブル（例 `booking_options`）: `tenant_id / name / duration_minutes / price_yen /
  description / enabled / sort_order`
- CHECK: 名前1〜40文字 / `duration_minutes` 0〜180 / `price_yen` 0〜1,000,000
- 追加時間の選択肢は5分刻み。先頭に **0分**（時間が増えないオプション。プロテイン等）
- 🔴 **料金 0 は「無料」ではなく「料金を表示しない」**。掲示したくない店・回数券に含む店がある
- RLS: 読みはそのテナントの在籍者、書きは owner/trainer。公開ページ用に anon 可の
  読み取り専用 RPC を1本
- 店の削除関数（`delete_my_gym` 相当）に DELETE を1行足す。
  🔴 **必ず最新の定義から全文コピーする**（古い版から写して他テーブルの DELETE を落とす
  事故がジムボードで実際に起きている）

### 第2段: お客様が選べる・占有に加算する

- 予約テーブルに `option_minutes`（NOT NULL DEFAULT 0・CHECK 0〜480）と
  `booking_options`（jsonb の控え）を足す
- 🔴 **控えには名前と金額も残す。** あとで店がマスタを直しても、過去の予約の内容が
  書き換わらないようにするため
- 上の「5つの場所」を全部直す
- 既定 0＝**オプションを使わない店の挙動は1分も変わらない**

### 第3段: 予定表で分かる・店があとから足せる

- 予定表のカードに「オプション付き」が分かる表示（狭いので1行に畳む）
- 店側が既存の予約にあとからオプションを足せる導線
- 🔴 **重複チェックが BEFORE INSERT だけなら、UPDATE で占有を伸ばしても何も検査されない。**
  次のお客様の枠を静かに飲み込む。**専用の BEFORE UPDATE トリガーを同時に足すこと**
  （ジムボードは `GB008`）
- 🔴 そのトリガーは**伸びる方向だけ**見る。`新しい合計 <= 古い合計 なら即 RETURN NEW`
  を関数の先頭に置く。これが無いと、キャンセル・担当変更・メモ編集など**あらゆる UPDATE**が
  この検査を通ってしまう
- 変更したらお客様に通知（プッシュ＋メール）。冪等キーは
  `option-change-<予約id>-<新しい分数>-<並べ替えたオプションid>` のような形にして、
  同じ内容の二重送信を止める。**変わっていない／過去の予約には送らない**

### 第4段（🔴 ここが本題）: 確認カードで毎回聞く

第2段では選択欄を**枠グリッドの手前**に置いた。占有が伸びる＝選べる枠が変わるので、
先に決めさせないと選んだ枠が無効になる——実装としては筋が通っていた。

**が、実店舗から出た指摘はこうだった:**

> オプションが分かりづらい、これは気づかない。下にスクロールしてオプションの存在に
> お客さんが予約する時に気づかない。毎回日にちを予約したときに、確認の時にオプションを
> 付けるか聞くようにしてください。それで後ろが埋まってたら、オプションの時間分予約を
> 早めるように文字を出す感じでいきましょう。

**お客様は日付を選んだ瞬間からグリッドへ向かってスクロールしていて、その途中にあるものは
読まれない。** 読まれるのは指が止まる場所——枠を押したあとに出る確認カード——だけ。

#### 決めたこと

```
枠グリッド … 素の枠（オプション無し）で作る
確認カード … 選んだ枠にオプションが入るかを、枠ごとに見る
```

- 選択欄は**確認カードの中、時刻表示のすぐ下**。ONにすると終了時刻と料金がその場で変わる
- 🔴 **ダイアログ（予約ボタンの後に聞く）にしない。** 絶対付けない人（多数派）にも毎回
  1タップ増え、「この内容で予約する」が最終確定でなくなる。カードの中なら付けない人は
  0タップで、気づく率は同じ場所なので変わらない
- 🔴 **グリッドをオプションで絞らない。** 絞ると「満枠」の意味が変わり、実際には空いている
  枠にキャンセル待ちが付く。ただし**予約変更（リスケ）中だけ**は引き継ぐ分数でグリッドを
  作る（0 にすると短い枠を「空き」と見せて DB に長さで断られる）
- 🔴 **選び直しても選択中の枠を外さない。** 外すと、毎回付ける人が枠を選び直すたびに
  付け直すことになる。（店側の代理予約は逆に「先に選ばせて絞る」ままでよい。電話で
  聞いてから入力する場面なので、提示する必要が無く、絞るほうが速い）
- 🔴 **ON でも入らない枠なら、送信する分数は 0 に倒す。**
  「画面に見えている内容 ＝ 送信する内容 ＝ 入ることを確かめた内容」を1本にする。
  そのうえで予約ボタンを押させない（黙ってオプションが外れるのを防ぐ）

#### 付けられないときに出すもの

**文字で「早めてください」と書くだけにしない。** お客様は画面を上に戻って別の枠を探し、
また予約ボタン、また同じ案内、の往復になる。混む時間帯では追加料金どころか
**基本の予約ごと落ちる**。

```
⚠ 21:30 のトレーニングはご予約いただけます
   ストレッチを付けるには、続けての時間に空きが足りません。
   [ 21:00 に変更してストレッチを付ける ]   ← outline
   [ ストレッチを付けずに 21:30 で予約する ] ← accent（逃げ道は必ず出す）
```

- 🔴 一文目は「この枠はダメ」ではなく**「基本の予約は取れる」**。色は赤ではなく警告色。
  以前 ON にしたまま忘れている人が赤い警告を見ると、枠自体が取れないと誤解して
  別の枠を探し回る（実際には基本だけなら取れる）
- 🔴 提案する時刻は**実際に付けられる枠を探した結果**。「30分前」を機械的に返さない——
  後ろの予約の位置によっては30分早めても足りず、押した先でまた断られる
- 🔴 提案の候補は**素の枠として取れるもの**だけ。締切・回数上限・受付しない帯で押せない枠を
  提案すると、押した瞬間に DB に断られる
- 早い側を優先（店の意図が「前に詰めてもらう」なので）。前に無ければ後ろを出す。
  どちらも無ければ「この日は付けられる時間がありません」
- 理由は**2種類だけ**: 「続けての時間に空きが足りない」と「営業時間（担当の勤務時間）を
  過ぎる」。🔴 **受付しない帯・締切・回数上限をここに出さない**——どれも開始時刻で決まる
  ので答えが変わらず、混ぜると店が意図的に閉めている帯の存在がお客様に見える

## 🔴 判定の本体を2箇所に書かない

確認カードの「この枠に入るか」は、枠グリッドの「この枠は取れるか」と**同じ式**でなければ
ならない。ずれると「空きに見えるのに送信すると断られる」＝何度押しても取れない画面になる。

ジムボードでは画面コンポーネントにあった判定の本体を **lib へ移した**（写したのではない）。
呼び出し側は薄い皮だけにする。**両方に本体があると必ず片方だけ直される。**
見張りテストで「画面側に判定の本体が残っていないこと」まで固定すること。

閉店の判定に使う長さは **1枠＋オプション**（間を入れない）。枠グリッドが最後の枠を出す
ときの長さと揃えないと、グリッドが出した枠をカードが「閉店を過ぎる」と言って弾く。

## 実際に踏んだ地雷

1. 🔴 **設定を保存すると、入れた直後の行を自分で消していた。** 保存は「更新→追加→削除」の
   3段で、最後の削除が「残す id 以外を消す」。ところが追加した行の insert に
   `.select("id")` が無く採番された id を受け取っていなかったため、**初回の追加では
   「残す id」が空配列**になり、条件なしの全削除に落ちていた。
   本番のテーブルは**全テナントで0件**＝どの店も1件も登録できていなかった。
   トーストは画面の状態だけ見て「保存しました」と出るので成功に見える。
   → **insert では必ず採番された id を受け取り、条件なしの全削除は「画面が0件のとき」
   だけに限る**（残す id の件数で判断しない）
2. 🔴 **その保存を見張るテストはあったのに通っていた。** 「削除は最後」という**順番**しか
   見ておらず、**削除の条件が正しいか**を1つも見ていなかった。
   → 書き込みの検査を本文検査（この文字列があるか）で済ませない。
   **偽のDBを相手に実際に保存を走らせて、行が生き残るかを見る**
3. 🔴 体験予約のトリガーが `NEW.option_minutes` で落ちる（上記）
4. 🔴 選択欄をグリッドの手前に置くと素通りされる（第4段の経緯）
5. 🔴 枠を押したあとの自動スクロールが `block:"center"` だと、カードにオプション欄が乗って
   画面より高くなった瞬間に**カードの上端＝オプション欄が画面の外に切れる**。
   「気づかない」がそのまま再発する。`block:"start"` にする
6. くり返し予約（毎週×N回）でオプション ON のとき、**入らない週は基本の予約ごと
   スキップされる**。カードにそう明記する。
   🔴 またスキップの理由は画面では区別できない（DB の拒否は「満枠」も「オプション分だけ
   入らない」も同じ経路・SQLSTATE 無しで返る）。**原因を断定しない文言**にすること
   （「満枠、またはオプションの時間が取れないためスキップしました」）
7. 他の端末が直前に後ろの枠を取っていると、画面の埋まり枠が古いままで「押しても取れない」が
   繰り返される。→ **DB に断られたら埋まり枠を取り直す**（枠は外さない。次の描画で
   「◯◯に変更して付ける」に切り替わる）
8. 予約の完了画面・予約一覧に**オプション名が一切残らない**と、終了時刻が延びている理由が
   分からず「間違えたかも」とキャンセル→取り直しが起きる。両方に出すこと
9. 開発用のフィクスチャが埋まり枠を返していなかったため、**空き枠の判定を画面で一度も
   確認できていなかった**。着手前に確認すること

## 検証（この作法を省かない）

- **本番は3段構え**: 読み取りで現状を出す → 実行する → **そのロールを演じて**実際に読む。
  書き込みは全部 `BEGIN … ROLLBACK`。**陽性の対照**を必ず同時に置く
  （0件ばかりで「全部効かない」を見誤らないため）
- 占有の境界を数字で固定する: 1枠60・間15・オプション30・後ろに18:00の予約がある日で
  「16:30 は素なら取れる／オプション付きだと取れない／16:15 なら取れる／
  終了ちょうど（19:15）から次を取れる」
- **変異検証**: 間を2回足す・閉店の判定に間を入れる・提案を遅い側優先にする・
  押せない枠も提案する・ブロック枠の特別扱いをやめる・担当の重なりを見ない——
  それぞれで見張りが赤くなることを確認する

## 残してよい既知の穴（ジムボードも直していない）

- 同時受け入れ数を時間帯で変える機能がある場合、画面も DB も**開始時刻の帯しか見ない**。
  17:00開始（2人まで）の予約が18:00以降（1人まで）に食い込んでも通る。
  画面と DB が一致しているので「押しても取れない」にはならない。直すなら両方同時に
