# 予約回数の制限（2026-08-21）

「平日の 18:00〜19:00 は1週間に1回まで」のように、**混み合う時間帯に
お一人が取れる予約の回数**を店が制限できる。

## なぜ必要か

Salute御所南で実際に起きた: 週2回来る会員が平日夜のピーク帯（18-19時）を
週2枠とも取ってしまい、**他の会員がその時間帯を一度も取れない**。
締切（bookingCutoff）は「手前」、受付開始時期（bookingWindow）は「先」を
締めるが、**「同じ人が同じ帯を取りすぎる」を締めるものが無かった**。

## ルールの形（`booking_frequency_limits`、1行=1ルール）

```
曜日の集合 × 時間帯 [start, end) × 期間（week/day）× 回数上限
  × 対象（user_id NULL=全員 / 非NULL=そのお客様だけ）× enabled
```

汎用なので同じ仕組みでこう使える:

| 使い方 | weekdays | 時間帯 | period | max |
|---|---|---|---|---|
| ピーク帯は週1回（本件の動機） | 平日 | 18:00-19:00 | week | 1 |
| 1日1回まで | 全曜日 | 00:00-24:00 | day | 1 |
| 全体で週2回まで | 全曜日 | 00:00-24:00 | week | 2 |
| 土曜午前は週1回 | 土 | 09:00-12:00 | week | 1 |

## 🔴 店側の代理予約には適用しない

トリガー（`guard_booking_frequency_limit`）は **auth.uid() = NEW.user_id の
自己予約だけ**を見る。代理予約（トレーナーが入れる）とサービスロール
（auth.uid() IS NULL。salute_sync 等）は素通し。

受付開始時期と同じ思想: お客様のセルフサービスを絞るのが目的で、
店が電話で受けて手で入れるぶんは店の裁量。**例外は店が作れる。**

この非対称は次の2つが**セットで**成立している。片方だけ変えると挙動がねじれる:
- DB: トリガー冒頭の `IF v_actor IS NULL OR v_actor IS DISTINCT FROM NEW.user_id THEN RETURN NEW`
- クライアント: TrainerSchedule は `exceededFrequencyLimit(` を**呼ばない**
  （`src/test/bookingLimits.test.ts` が両方を見張る）

⚠️ トレーナーが代理予約で**自分自身を**お客様として選ぶと auth.uid() = user_id に
なり制限を受ける。TrainerSchedule はこのとき専用文言
（`bookingLimits.errorOverLimitProxy`）で設定画面へ誘導する。

## 判定の規則（クライアントと DB で同一。テストが一致を見張る）

- **予約の開始時刻**が [start, end) に入るか。18:00-19:00 は 18:00〜18:59 開始に
  効き、**19:00 開始には効かない**（半開区間）。終わる時刻は見ない
  （説明できない制限は現場で使われない）
- 週は **JST・月曜始まり**。DB は `date_trunc('week')`（ISO週）、クライアントは
  `(wd + 6) % 7` で月曜へ戻す。このアプリの週は全箇所 `weekStartsOn: 1`
- 数えない予約は `status = 'キャンセル済み'` **だけ**。
  **'同日キャンセル済み'（消化）は数える**（満枠判定 check_booking_overlap と
  同じ除外規則。消化はセッションを使った扱いなので、その週のピーク帯の権利も
  使ったと数えるのが公平）
- **リスケは対象**（日時が変わる UPDATE を見る）。空いている時間で取ってから
  ピーク帯へ動かす抜け道を塞ぐ。ただし動かしている予約自体は
  `b.id IS DISTINCT FROM NEW.id` で除外＝同じ週内の移動は超過にならない
- 日時が変わらない UPDATE（キャンセル・メモ・担当変更）は見ない
- 全体ルールと個別ルールは **AND**（すべて満たす）。個別＝そのお客様への
  **追加の**締め付けで、上書きではない。「特定の人だけ緩める（免除）」は
  今回は持たない（必要になったら exempt 列を足す）

## SQLSTATE は GB003

| コード | 意味 | お客様への案内 |
|---|---|---|
| GB001 | 担当が同時間帯に別予約 | 別の時間なら取れる |
| GB002 | 担当がシフト外 | 別の担当か別の曜日 |
| **GB003** | **回数の上限** | **別の時間帯なら取れる** |

判定は `isBookingLimitError`（`src/lib/bookingLimits.ts`）。文言一致にしない。

## RLS（プライバシー）

- 🔴 **お客様には「全員向け」と「自分あて」しか見せない。** 他のお客様の個別
  ルールが見えると「あの人は制限されている」が同じジムの会員に漏れる
- 店側（owner/trainer）は全行見える。書けるのも店側だけ
- anon は一切見えない（公開ページに制限の概念は無い。trial_bookings は
  user_id を持たないゲストなのでトリガー自体を付けていない）

## 画面

- 設定 → 「予約回数の制限」（`TrainerBookingLimits.tsx`）。追加の既定値は
  実店舗の典型例（平日 18-19時・週1回）をそのまま出す。保存は
  「テナントのルールを丸ごと消して入れ直す」（スタッフのシフトと同じ）
- 予約側（CustomerBooking）は枠に「上限」表示を出して押せなくする＋送信直前にも
  再判定（他端末との競合向け。最終判定は DB）。**上限の枠はキャンセル待ちの
  対象にもしない**（空きを待っても自分は取れない）
- 読めない環境（マイグレーション未適用等）は**空配列＝制限なし**に倒す
  （`useBookingFrequencyLimits`）。予約を止めない。DB が最終判定なので抜け道に
  ならない

## 本番適用（2026-08-21）

適用済み（`20260821020000_booking_frequency_limits.sql`）。実挿入で確認
（すべて ROLLBACK。owner / お客様A / お客様B を演じ分け）:

| ケース | 期待 | 結果 |
|---|---|---|
| 週1ルール・同週2件目（自己） | GB003 | ok |
| 時間帯外 17:00 / 境界 19:00 開始 / 翌週の同帯 | 通る | ok（4/4） |
| 🔴 同じ2件目をオーナーが代理で | 通る | ok |
| 個別ルール: B は同帯2件通る / A は2件目拒否 | | ok |
| enabled=false | 通る | ok |
| period='day': 別日は通る / 同日2件目拒否 | | ok |
| RLS: owner=2件 / A本人=2件 / B=1件（Aの個別が見えない） | | ok |
| お客様の UPDATE | 0行 | ok |

適用後、`booking_frequency_limits` は **0件**（どの店も制限なし＝従来どおり）。

### ⚠️ Lovable query_database の 499 は「失敗」と限らない（2026-08-21）

適用中、`499 request_cancelled` が5回出たが、**うち4回はサーバー側で適用済み**
だった（応答だけが切れる）。499 が出たら再実行する前に**必ず現物を照会する**
（同じ CREATE POLICY を二重実行すると already exists で別のエラーになる）。

## 検討したがやらなかったこと

- **時間帯別のキャパシティ**（ピーク帯だけ同時受け入れを絞る）: 別機能。
  booking_capacity の帯別上書きとして将来やる余地あり
- **プラン連動の回数上限**（月8回プラン等）: 性質が違う（枠の公平性ではなく
  契約の消化管理）。planUsage 系の話
- **特定のお客様の免除（緩める側）**: exempt 列を足せば載る設計にしてある
