# 顧客の活動タイムライン（2026-08-26）

カルテの概要タブ。ロードマップのフェーズ1-⑦。

## 直した困りごと

カルテはタブが7本あり、来店・記録・測定・入金・同意が**別々の場所**にある。
セッション前に知りたいのは「前回いつ来て、何をして、体重はどうで、入金は済んでいるか」で、
そのために**4回タブを行き来していた**。

⚠️ **追加ではなく集約**。元のタブは残す（詳しく見る・編集するのはそちら）。
ここは「読むだけ」で、何も書き換えない。

| ファイル | 役目 |

## 🔴 気をつけたこと

### 1. 日付だけの列を UTC として読まない

`bookings.booking_date` は timestamptz だが、`workout_date` / `measured_date` /
`paid_on` / `agreed_on` / `taken_date` は **date 型**。

`new Date("2026-08-26")` は **UTC の 0 時**として解釈される。そのまま JST で表示すると
9時間ずれて**前日になる**。`dateOnlyToIso` で JST の 0 時にそろえる。

### 2. トレーニング記録は日ごとに畳む

`workouts` は**1回のセッションで種目ぶんの行**ができる（10種目なら10行）。
そのまま出すと、その日のタイムラインが記録だけで埋まって、来店も入金も見えなくなる。
日ごとに1件へ畳んで「◯種目」と出し、種目名は先頭3つまで。

### 3. 一意キーは種類で名前空間を切る

`id` は別テーブルなので、測定と入金が**同じ id を持ちうる**。
`measurement:<id>` のように接頭辞を付けないと React の key が衝突して描画が壊れる。

### 4. 1種類が失敗しても他は出す

6種類を `Promise.all` で並行に取り、1つ失敗しても握って空配列にする。
**カルテが真っ白になるより「入金だけ出ていない」ほうが害が小さい。**

### 5. キャンセルも残す

来なかったことも事実で、店が知りたい情報。色を弱めて（`text-muted-foreground/60`）
起きなかったことだと分かるようにするだけにした。

## 件数

- 種類ごとに直近60件（`PER_KIND`）
- 混ぜたあと40件（`TIMELINE_LIMIT`）
- 画面は最初5日ぶん（`INITIAL_DAYS`）、「さらに見る」で全部

通い続けているお客様ほどカルテが重くなるのを防ぐ。タイムラインは
「最近どうだったか」を見るものなので、全部読む必要が無い。

## 変異検証

| 変異 | 落ちた |
|---|---|
| 日付だけの列を UTC 扱いにする | ok |
| トレーニング記録を畳まない | ok（3本） |
| 本人（user_id）の絞りを外す | ok |
| 一意キーに種類の接頭辞を付けない | ok |

## ⚠️ 入れていないもの

- **通知（`email_send_log`）。** 宛先がメールアドレスで、クライアントは
  そのお客様のアドレスを知らない（`profiles` に email 列が無い）。
  出すなら user_id で引けるようにするか、サーバー側で突き合わせる必要がある
- **チャット（`messages`）。** 件数が多く、タイムラインが会話で埋まる。
  「やり取りがあった日」だけ出すなら畳み方を決める必要がある
- **体験（`trial_bookings`）。** 入会前の記録で、`user_id` を持たない
  （アカウント作成前のため突き合わせる鍵が無い）
