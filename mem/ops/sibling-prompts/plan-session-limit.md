# プランの回数上限を強制できるようにしてください

ジムボード（このアプリの元）で 2026-08-21 に実装・本番稼働済みの仕様を独立実装します。
決定事項は変えず、名前・SQLSTATE・文言はこのアプリの現物に合わせてください
（SQLSTATE は migrations を grep して未使用の `GB0xx` を2つ確保: 上限用と契約ガード用）。

## 前提の確認（先に grep すること）

このアプリの契約プラン（tenant_plans 相当）に `max_sessions` と `allow_overflow` が
あるか、お客様（profiles 相当）に `cycle_start_date`（利用期間の起算日）があるかを
確認する。あるはず（フォーク元由来）。「残り0回」の表示まであって**押せば予約できる**
＝表示だけで未強制、が出発点。

## 仕様（決定済み・変えないこと）

1. **`allow_overflow` を実装に繋ぐ**（新しい列は足さない）:
   - `true` / `NULL`（既定・既存の全プラン）… 今までどおり超過できる。**何も変わらない**
   - `false` … DB トリガーが専用 SQLSTATE で拒否
2. **数え方はクライアントの表示と同一**にする（別に数え直すと「カードは残1回と
   言うのに拒否される」が出る）:
   - 窓 = 起算日からの**応当日ベースの月次窓・応当日そのものは前サイクルに含む**
     （end は応当日の翌日＝排他的上限）。SQL 関数（例: `plan_cycle_window`）に切り出す
   - 猶予（grace_days 相当があれば）: `lent = min(前サイクルの残り, 猶予帯の件数)` を
     今サイクルの消化から差し引く
   - 除外は「キャンセル済み」相当のみ（同日キャンセル＝消化は数える）
   - 判定基準日は**予約しようとしている日**（「今日」基準にすると、使い切った
     お客様が次サイクルの日付まで塞がれる。実レビューで発覚）
3. **サブスクだけに効かせる**（回数券は購入日起算・期間プランは無制限で窓が別物）。
   トリガー・設定画面・クライアント判定の3箇所すべてで絞る
4. **代理予約・サービスロールは素通し**（auth.uid() = user_id の自己予約だけ見る）。
   同時リクエストは advisory lock で直列化
5. 🔴 **`allow_overflow=false` ではサイクルの自動ロールを止める**（クライアント両側）。
   「使い切ったら次のルーティンへ進む」表示ロジックがあるはず。拒否する設定で
   ロールしたままだと、設定 ON の瞬間に既に超過しているお客様へ「残7回と表示される
   のに拒否される」が**必ず**出る（店が ON にするのはまさに超過しているから）。
   起算日を**書き換える側**（予約時の自動リベース）も同じフラグでゲートする——
   読む側だけゲートすると、**代理予約1件で起算日がロールして上限がリセットされる**
   （実レビューで発覚した穴）
6. 🔴 **契約フィールドの自己改変ガード**（もう1つの SQLSTATE）:
   判定材料（plan / cycle_start_date / grace 系）は**本人が UPDATE できる列**なので、
   会員が自分で書き換えれば上限を無効化できてしまう。BEFORE UPDATE トリガーで
   **本人の自己更新だけ**を拒否する:
   - plan / grace 系の変更 … 常に拒否
   - cycle_start_date … NULL→値の初回設定は許可（予約時の自動設定が正規動線）。
     既に値がある行の変更は allow_overflow=false のプランの会員だけ拒否
   - 店側（auth.uid() ≠ user_id）とサービスロールは素通し。店側の人間が自分自身の
     行を触る場合は tenant_members の owner/trainer 在籍で判定
     （🔴 profiles.tenant_id で判定しない——NULL の会員が実在し、本人が書ける列
     なので根拠にできない）
7. 非公開（is_active=false）プランの会員も判定材料を失わないこと。お客様側の契約
   解決は**全行**（非公開含む）から引く。DB を is_active で絞る方向は採らない
   （非公開にした瞬間に上限が黙って外れる）
8. 定期予約・予約変更の経路でスキップ理由を区別して案内する（「満枠」と誤案内しない）

## 検証

- 変異検証: 窓の +1（応当日）・ロールのゲート・自己改変ガードの各条件を壊して赤を確認。
  SQL の検査は **RETURN QUERY の行だけ**を見る（全体 grep だと WHILE ループ内の
  類似式にマッチして素通りする——実際に踏んだ）
- 本番3段構え: 全プランが既定（true/NULL）のまま＝挙動不変を先に確認 → 適用 →
  会員/店/サービスロールを演じ分けて GB004/GB005 相当の全経路を確認
  （すべて BEGIN…ROLLBACK）
- migration はマージ直前に本番へ適用（types.ts 再生成レース）
- ゲートグリーン → PR → マージ
