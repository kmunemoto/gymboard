# 会員を体験予約から会員アプリへ案内する

Saluteの既定体験予約サイト（`/trial` と同じ店舗の `/trial/:tenantId`）だけで、
名前入力後に `trial-book` の `check_only: true` を呼び出す。
対象名なら日時選択・予約ボタンを会員向けの案内に置き換え、アプリ起動・
ストア・Webログインへのリンクを表示する。他店舗では事前確認を呼び出さない。
氏名を入力し直したら再確認し、古い応答は無視する。
最終POSTからの拒否を、遅れて届いた事前確認の応答で解除しない。

## 既存予約を維持する設計

- DBのテーブル、RLS、RPC、予約データ、トリガーは変更しない。
- 空き枠、入力検証、締切、回数制限、重複防止、保存・通知は既存処理を維持する。
- 事前確認が通信失敗・未対応の旧APIだった場合も通常の予約送信を妨げない。
  最終POSTはサーバーの非公開設定を必ず再確認し、対象名を保存・通知前に拒否する。
- 判定に追加のDB問い合わせ・外部通信は使わない。
- `check_only: true` は予約・通知もDB問い合わせも行わない。

氏名パターンは Lovable Cloud の **Secrets** に `TRIAL_MEMBER_REDIRECT_RULES` として保存する。
値は「店舗UUIDをキー、氏名の部分文字列の配列を値に持つJSONオブジェクト」。
設定した店舗だけで判定する。1店舗あたり50件以下、1文字列100文字以下。
NFKC、ひらがな→カタカナ、空白・中黒等の除去後に部分一致で判定する。
短いパターンは別人にも一致し得るので、設定は店舗の依頼どおりに行う。
これは入力名に基づく予約経路の案内であり、本人確認ではない。

本番のお客様の氏名は、この公開リポジトリ・テスト・PR・Lovable依頼文に記載しない。
フロントに渡すのは判定結果だけ。設定や入力名をログに出さない。
Secretsは `VITE_` を付けず、Lovableの安全な設定画面に直接入力する。
公式手順: https://docs.lovable.dev/features/secrets

## 本番反映と確認

1. CI通過後にPRをマージする。DBマイグレーションは不要。
2. `trial-book` を `_shared/trial-member-redirect.ts` とともに再デプロイする。
3. 対象店舗だけの設定を Cloud → Secrets に登録する。公開チャットに値を貼らない。
4. 実デプロイに check_only を送り、指定された各表記が `member_booking_required`、
   対象外名・他店舗が `ok:true` になることを確認する。
   予約・通知を作るPOSTは本番テストに使わない。
5. フロントを Publish し、名前入力後の案内とリンクを確認する。

設定なし・JSON不正の場合は、通常予約を止めず、この制限だけを無効にする。
**その状態では対象名も予約できるため、4の実機能確認が済むまで完了扱いにしない。**
不具合時はこの新規Secretを削除すれば従来の受付に戻せる（既存Secretsは変更しない）。
フロントが先に公開されても旧APIの検証エラーが通常の予約操作を止めることはないが、
制限を有効にするにはサーバーの配置とSecret設定の両方が必要。
GitHubのマージだけではEdgeデプロイ・設定・Web公開の完了にはならない。

公開Webページの修正なので、ネイティブアプリの再リリースは不要。
アプリ起動は既存のカスタムスキームを使い、起動後は「予約」を開くよう案内する。
