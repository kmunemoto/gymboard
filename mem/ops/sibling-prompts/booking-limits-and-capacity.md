## 機能1: 予約回数の制限（曜日×時間帯×期間ごとの上限）

「平日 18:00〜19:00 は週1回まで」のように、**お一人あたり**の予約回数を制限する。

- 専用テーブル（例: `booking_frequency_limits`）:
  `tenant_id / weekdays INTEGER[]（0=日〜6=土）/ start_time / end_time /
  period（'week'|'month'）/ max_count / enabled / exempt / user_id`
- 🔴 **時間帯は閉区間 [start, end]**——「〜19:00」は**19:00 に始まる回まで**含む。
  実店舗が「19:00 開始が素通りする」と実感したため半開区間から変えた決定。
  マッチ・既存予約の数え・免除の3箇所**セット**で閉区間にしないと判定が自己矛盾する
- BEFORE INSERT OR UPDATE トリガーで拒否（専用 SQLSTATE）。
  **お客様の自己予約だけ**に効かせる（`auth.uid() IS NULL OR ≠ NEW.user_id` は素通し
  ＝店の代理予約とサービスロールは店の裁量）
- UPDATE は「日時が変わるとき」と「キャンセル済み→復活」だけ判定
  （キャンセル行を置いて枠を確保するバイパス封じ）
- 同一人物の同時リクエストは `pg_advisory_xact_lock` で直列化
- 週の起点・曜日・分は **JST**（`AT TIME ZONE 'Asia/Tokyo'`）
- クライアントにも同じ判定を実装して**事前に**枠をグレーにする（判定式は共有関数に
  集約し、SQL と一致することをテストで見張る）。エラー検出は必ず `error.code`

## 機能2: 時間帯別の同時受け入れ数

店全体の同時受け入れ数（tenants の capacity 相当）を、**曜日×時間帯で上書き**する。

- 専用テーブル（例: `booking_capacity_windows`）:
  `tenant_id / weekdays / start_time / end_time / capacity / enabled`
- 🔴 **区間は半開 [start, end)**。機能1と違う理由: こちらは「その時間に居る
  スタッフの数」なので、12時に帰る応援の帯を 12:00 開始の枠に効かせてはならない。
  **区間規則は機能で使い分ける**（制限=閉・キャパ=半開）。テストで両方固定する
- 解決順: ①開始時刻に当てはまる有効な帯を探す → ②あれば**最小の capacity**
  （厳しいほうが勝つ。最大にすると「絞る帯」が広い帯に負けて効かない）→
  ③無ければ従来の既定値
- DB は既存の重複チェック関数（check_booking_overlap 相当）から呼ぶ形に切り出し、
  クライアントは共有関数1本。**公開ページ（体験・ゲスト予約）にも効かせる**——
  anon には表を開けず、読み取り専用 RPC を1本用意する
- 既定は帯0件＝**どの店の挙動も変わらない**

## 機能3: 特定のお客様の免除（制限を緩める側）

機能1の全員向けルールから、**特定のお客様だけを外す**。

- 機能1のテーブルに `exempt BOOLEAN`（既定 false）を追加。true の行は「制限」では
  なく「免除」
- 🔴 **判定は免除が先**。マッチする免除が1件でもあれば制限を一切受けない
  （逆順にすると免除を作る意味が無い）
- 🔴 `CHECK (NOT exempt OR user_id IS NOT NULL)`——「全員を免除」の行は禁止
  （ルールを消すのと同じで、並ぶとどちらが効くのか行を見ても分からなくなる）
- 免除にも曜日・時間帯を持たせる（「この人は平日夜だけ免除」が表現できる）
- 「受付しない時間帯」（別プロンプト）を実装済みなら、免除はそれより強い

## UI の決定事項

- 設定画面の時刻セレクタは **15分刻み**（30分刻みだと 18:15 のような境界が
  設定できない、という実店舗の指摘があった。#330）。保存済みの刻み外の値は
  黙って丸めず選択肢に含める
- 設定 UI はロールに合わせてこのアプリの設定画面へ。文言は5言語

## 実際に踏んだ地雷

- `array_length('{}', 1)` は **NULL** を返し CHECK を素通りする。曜日配列の検証は
  必ず `cardinality`
- テナント削除関数（delete_my_gym 相当）に新テーブルの DELETE を足すとき、
  **必ず最新の定義から**全文コピーする。古い版から写して他のテーブルの DELETE を
  落とす事故が実際に起きた（見張りテストが捕まえた）。repo と本番の定義の
  一致テストも足す
- クライアント判定のテストは「免除の EXISTS」と「制限のループ」を**切り分けてから
  1条件ずつ**固定する。全体への toMatch だと片方が消えても緑のままになる
- トリガー関数は SECURITY DEFINER + `SET search_path = public` +
  `REVOKE ALL FROM PUBLIC, anon, authenticated`。RLS はテナント境界 RESTRICTIVE、
  書き込みは owner/trainer のみ

## 検証

- 変異検証（判定の向き・区間の開閉・免除の先行・advisory lock それぞれを壊して赤）
- 本番3段構え: 適用 → お客様/オーナー/anon を演じ分けて実書き込み
  （すべて BEGIN…ROLLBACK）。「制限に当たって拒否」「免除で通る」「代理は素通し」
  「端の時刻の扱い」を最低限確認
- migration は**マージ直前に本番へ適用**（types.ts 自動再生成との競合を避ける）
- ゲート（このアプリの CI と同じコマンド）グリーン → PR → マージ
