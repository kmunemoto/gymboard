# 顧客のCSV一括登録（2026-08-25）

ジム設定 → データの書き出し・取り込み（オーナー限定）。
ロードマップのフェーズ1-②。他ジムからの乗り換えの入口。

## 🔴 「アカウントを持たない顧客」は作れない

最初は `profiles.user_id` を NULL 許容にして、店だけが見る未招待の顧客を作る案で進めた。
**本番を実測した結果、その案は成立しないと分かった。**

| 事実 | 根拠 |
|---|---|
| 顧客一覧の起点は `profiles` ではなく `tenant_members` | `src/hooks/useProfile.ts:198-271`。行集合は `customerIds.map` で決まる |
| `tenant_members.user_id` は NOT NULL ＋ FK → `auth.users` | 本番の DDL |
| 予約を入れると `ensure_customer_on_booking` が `profiles` と `user_roles` に INSERT。どちらも FK → `auth.users` | 本番の関数定義 |
| 人数上限は `tenant_members` を数える | `enforce_tenant_member_limits` |
| プラン・起算日は `profiles` 側（`tenant_members` の同名列は誰も読んでいない） | `guard_booking_plan_limit` / `TrainerClientDetail` |

つまり `user_id` を NULL にした行は **一覧に出ず・予約も記録もぶら下がらず・
人数上限にも当たらない**、どこからも触れない行になる。
`bookings` に FK が無いので架空の uuid なら通りそうに見えるが、
BEFORE INSERT トリガが `user_roles`（FK あり）に書きに行くので必ず落ちる。

## 採った形: 裏でアカウントだけ作る

取り込み時に、**ログイン手段を持たない `auth` のアカウント**を1件ずつ作る。

- メールは配達できないプレースホルダ（`csv-import+<uuid>@gymboard.invalid`）
- パスワード無し・ソーシャル連携無し・確認メールも送らない＝**ログインできない**
- 通知は一切飛ばない（宛先が存在しない）

DB から見れば普通の顧客なので、**一覧・カルテ・予約・記録・プラン上限・削除・RLS が
1行も直さずにそのまま動く**。乗り換え元の来店履歴や回数券残も後から入れられる。

「未招待」は状態として持つ:

| 列 | 意味 |
|---|---|
| `profiles.imported_at` | CSV で作られた行なら、その時刻 |
| `profiles.claimed_at` | 本人が実際にログインした時刻 |

`imported_at` があって `claimed_at` が NULL の間が「未招待」。一覧にバッジが出る。

⚠️ 紐づけは**氏名照合ではなくアカウントの引き渡し**。
店が招待を送った先の人がログインする＝その人のアカウント、なので
「同姓同名で他人のカルテが見える」が原理的に起きない。

## 決めたこと

- **オーナー限定。** 画面が「データ」カテゴリ（オーナー限定）の中にあるのと、
  一括登録が有料プランの席を大量に消費する操作だから。
  スタッフにも開くなら画面と Edge Function の**両方**を同時に変える（片方だけだと 403）
- **1回の呼び出しは100件まで。** アカウント作成は admin API を1件ずつ叩くので、
  多いと関数の実行時間に当たる。画面が分割して繰り返し呼び、進み具合を出す
- **1回の呼び出しの中は全部入るか1件も入らないか。** 人数上限に当たったときに
  半端な行が残らない。どこまで入ったかは件数で正確に言える
- **失敗したら作ったアカウントを消す。** ここが漏れると、どのテナントにも属さない
  幽霊アカウントが `auth` に溜まる
- **必須は「名前」だけ。** 他は空でよい。在籍状態の未記入は在籍中に倒す
- **重複は取り込まない。** 電話番号（数字だけで比較）、無ければ名前で突き合わせる。
  退会した人も突き合わせの対象にする（取り込み直すとカルテが2つに分かれるため）

## 踏んだこと

### 1. 🔴 休会・退会が本番で一度も書けていなかった

`tenant_members.status` に CHECK が2本付いていて、通る値が積集合
（`active` と `cancelled` だけ）になっていた。休会の顧客を取り込もうとして発覚。
別PRで先に直した（`20260825000500_fix_member_status_check.sql`）。

### 2. Windows の Excel は Shift_JIS で書き出す

他システムから出した名簿はまずこれで来る。UTF-8 として読めなければ Shift_JIS とみなす
（`decodeCsvBytes`）。ジムボード自身の書き出しは UTF-8 + BOM なのでそのまま通る。

### 3. 数式インジェクション対策の `'` を外さないと往復できない

書き出し側は `=` `+` `-` `@` で始まる値の先頭に `'` を足す（`csvExport.escapeCsvValue`）。
読み取りで外さないと、書き出し→読み戻しを繰り返すたびに `'` が積もる。

## 招待（2026-08-25 に追加）

カルテの概要タブに「アプリに招待する」カード（オーナー限定・取り込み済み＆未ログインの人だけ）。
店が本人のメールアドレスを入力して送ると:

1. `invite-customer`（Edge Function）がアカウントのメールを本人のアドレスに差し替える
   （`email_confirm: true` ＝「店がこの宛先を保証する」の意）
2. GoTrue の recovery リンクを `generateLink` で作り、既存の `/reset-password` に合流させる
   （`?flow=invite` で見出しだけ「はじめまして」に変わる。仕組みは再設定と同一）
3. `customer-invite` テンプレートで招待メールを送る（**CLIENT_ALLOWED_TEMPLATES に入れない**。
   宛先が自由入力なので、クライアントから呼べると任意の宛先にメールを撒ける口になる）
4. 送信に**成功したときだけ** `profiles.invited_at` を記録（バッジが 未招待 → 招待済み に変わる）

本人がリンクからパスワードを設定してログインすると、useProfile の `claim_my_profile` が
走って `claimed_at` が入り、バッジもカードも消える。

### 決めたこと

- **invite 種別は使えない。** GoTrue の invite は新規ユーザー専用で、
  既に存在するこのアカウントには発行できない。recovery で代用する
- **既に使われているアドレスは `email_taken` で返す。** その人は自分のアカウントで
  ログインすればよい。無理な紐づけ（マージ）はしない
- **配信停止リスト（過去に不達）は成功扱いにしない**（`email_suppressed`）
- **リンク切れの救済は本人に持たせる。** メール本文に「パスワードをお忘れの方から
  やり直せます」を書いてある。アドレスは設定済みなので self-service recovery が効く
- ⚠️ **宛先の打ち間違い＝別人にアカウントが渡る。** 送信前の confirm で宛先を読み上げ、
  メール本文に「心当たりが無い場合は破棄」を必ず入れる。これが唯一の防波堤

### デプロイ（2026-08-25）

`invite-customer` は Lovable のエージェントに依頼してデプロイ済み。

| 叩いた先 | 依頼前 | 依頼後 |
|---|---|---|
| `invite-customer`（今回） | **404** NOT_FOUND | **401** Unauthorized |
| `import-customers`（対照） | 401 | 401 |

⚠️ **依頼から反映まで数分かかる。** 直後に叩くと 404 のままなので、
1回で決めつけずに間を置いて叩き直すこと（今回も1回目は 404 だった）。

⚠️ `send_message` は `wait: false` で投げる。既定の待機は MCP 側が60秒で
切るが**依頼自体は届いている**ので、投げ直すとクレジットを二重に使う。

## Edge Function のデプロイ

🔴 **push でも Publish でも本番に出ない。** Lovable のエージェントに頼むしかない。
頼んだあと必ず自分で叩いて 404 でないことを確かめる（`mem/ops/edge-function-deploy.md`）。

**2026-08-25 にデプロイ済み。** DB から `net.http_post` で確認:

| 叩いた先 | 依頼前 | 依頼後 |
|---|---|---|
| `import-customers`（今回） | **404** NOT_FOUND | **401** Unauthorized |
| `signup-trainer`（対照・デプロイ済み） | 401 Unauthorized | 401 Unauthorized |

依頼前は対照と食い違い、依頼後は一致した＝デプロイされた。
401 は `verifyCaller` が未認証を弾いている正しい応答。

⚠️ `mcp__Lovable__send_message` は 60 秒で MCP 側がタイムアウトするが、
**依頼自体は届いている**（`list_messages` で `status: accepted` を確認）。
タイムアウトしても投げ直さないこと（クレジットを二重に使う）。
