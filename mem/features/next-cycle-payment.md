# 次回分の入金まで、次回分の予約を受け付けない（店ごと ON/OFF・既定 OFF）

## 何をしているか

2026-09-22 の宗本さんの要望:

> お店側が次回分の料金を払ってないと次回分の予約が取れないようにするシステム。
> 今回の最後の予約時に次回の支払いをしてもらい、次回分の予約が取れるようになる。
> まだ今回の予約の途中だけど次回分の予約を取りたいなら……支払う。

## 🔴 規則は1文にした

> 次回分の予約は、次回分のお支払いが確認できてから取れる。

**「最後の予約のときに払う」は決まりではなく、いちばん多いタイミングというだけ。**
途中で払ってもいい。**「どれが最後の予約か」をアプリに判定させない**——
キャンセルや日時変更で動くので、判定すれば必ずズレる。見るのは「払ったか」だけ。

### 落とした案: 「次回の1回目までは払わずに取れる」

同じ日に検討して**落とした**。
その場で払う店（対面）だと「払いに来るための予約が取れない」矛盾が出るので
逃げ道として考えたが、**今回の途中でも払える**ので逃げ道が要らない。
残すと規則が2文（「ただし1回目だけは…」）になり、
**1回分を払わずに受けられる穴**が構造として残る。同じ提案をもう一度持ち込まないこと。

## 何が「次回分」か

**暦のサイクル窓**（`plan_cycle_window` / `getCycleWindow`）。起算日の応当日ベース。

⚠️ 画面の「利用期間」（`resolveEffectiveCycle`）の**使い切りロールは使わない**。
あちらの移動先は「(上限+1)回目の予約日」なので**予約が入って初めて決まる**。
「その予約を入れていいか」を決める側が参照すると循環する。

⚠️ 窓は `[start, start+1ヶ月+1日)`。応当日は窓に含まれ、次の窓はその翌日から始まる
（起算日 9/17 なら `[9/17, 10/18)` `[10/18, 11/19)` `[11/19, 12/20)`）。
アプリ全体で既にこの暦なので、**ここで別の暦を作らないこと**。
表示は必ず終わりの前日にする（`formatCycleRange`）。

回数の超過そのもの（月4回の5回目）を止めたいなら、それは既にある
`tenant_plans.allow_overflow = false`（GB004）の仕事。**別の設定として重ねられる**。

| 設定 | 止めるもの |
|---|---|
| `allow_overflow = false` | 今サイクルの5回目（GB004） |
| `next_cycle_payment_required` | 次サイクルの予約を、入金まで（GB009） |

## 誰に効くか（GB003/GB004/GB006/GB007 と同じ非対称）

| | |
|---|---|
| お客様の自己予約 | **止まる** |
| 店側の代理予約 | **止まらない**（「払い忘れたけど次回もらう」は店の裁量） |
| 体験・ドロップイン | 無関係（`trial_bookings` は別テーブル・トリガー無し） |
| 既存の予約 | **一切触らない**。止まるのは新規と日時変更だけ |

## 🔴 ONにした時点で進行中のサイクルは「払い済み」扱い

`tenants.next_cycle_payment_required_since` に ON にした日を入れ、
**その日までに始まっていた窓は払い済みとみなす**。

これが無いと、**ONにした瞬間に在籍会員が全員まとめて予約できなくなる**
（本番の Salute御所南で 38 人）。偽の入金行を作らずに初日を乗り切るための1列。
**OFF にしても `since` は消さない**（消すと OFF→ON のたびに全員が止まる日を作る）。

## 判定は DB の関数1本だけ

```
member_first_unpaid_cycle_start(tenant_id, user_id) → date | NULL
  「この日以降の予約には次回分の入金が要る」1つの日付。NULL＝止めるものが無い。
```

**お客様の画面（RPC `get_my_next_cycle_payment_gate`）も、予約のトリガー（GB009）も
同じこれを呼ぶ。** 規則を画面側に写さないので
「画面は取れると見せたのに DB が断る」が構造的に起きない。
`src/lib/nextCyclePayment.ts` にあるのは、その**1つの日付の使い方**だけ。

窓は今日の窓から順に前から見て、払い済みなら次へ進む。
**飛ばして先のサイクルだけ払っても開かない**（順番に払う、が規則）。

## 入金の記録は「素の ON/OFF」ではない

見た目はカルテのスイッチだが、中身は `member_payments` に1行足すこと。
`covers_cycle_start` が**どのサイクル分か**を持つ。

素のフラグ（`profiles.paid_this_month` のような1ビット）にすると、
次のサイクルが来ても ON のままで、**毎月 全会員ぶん手で戻す**ことになり必ず忘れる。
忘れた瞬間、**誰も止まらない仕組み**に変わる。
行として持てば、サイクルが進むだけで自動的に「未入金」へ戻る（戻す作業がゼロ）。

だからラベルに**期間を出す**（「次回分（10/18〜11/18）の入金」）。
何を確認して押したのかが、押す前に分かる形にする。

`(tenant_id, user_id, covers_cycle_start)` に部分一意索引があるので二重記録にならない。
既存の入金行は `covers_cycle_start = NULL`＝サイクルに紐づかない履歴（入会金・都度払い等）。

## 払い方はシステムに持ち込まない

システムが知るのは「**店が、次回分を受け取ったと確認した**」その一点だけ。
現金でも振込でもカードでも、店が押した瞬間が真実。払い方は記録のメモに残すだけで、
判定には使わない。振込の店で変わるのは「振り込んでから店が確認して押すまでの
タイムラグ」だけで、それはシステムではなくその店の運用。

だから文言も払い方を決めつけない:
**「次回分のお支払いの確認後にご予約いただけます」**
（対面の店なら「次回来店時に」、振込の店なら「振り込んで確認されたら」と読める）。

## 本番で確かめたこと（2026-09-22・3段構え・10件）

ロールを演じて `BEGIN … ROLLBACK` で実測。**対照（通るべきものが通ること）も毎回入れた。**

| | 結果 |
|---|---|
| OFFのまま gate | NULL（止めない）✓ |
| ON にした gate | 2026-10-18（次の窓の頭）✓ |
| 別テナントの会員（対照） | NULL ✓ |
| 会員・今サイクル 10/10（対照） | 通った ✓ |
| 会員・次サイクル 10/20（未入金） | **GB009** ✓ |
| 店の代理予約・次サイクル 未入金（対照） | 通った ✓ |
| 入金後の gate | 2026-11-19（次の次）✓ |
| 入金後・会員・次サイクル（対照） | 通った ✓ |
| 会員・次の次 11/20（未入金） | **GB009** ✓ |
| OFFに戻した gate（対照） | NULL ✓ |

全てロールバック済み。**本番でこの設定を ON にしたテナントはまだ無い**
（`member_payments` も 0 件のまま）。

## 見張り（`src/test/nextCyclePayment.test.ts`・35件）

変異5件（ONにした日を書かない／猶予の比較を外す／代理予約も止める／判定を写す／
サイクルに紐づけず保存）が赤になることを確認済み。

### 付随して直したもの

- **`src/test/rpcCallerCheck.test.ts` の穴を塞いだ。**
  `20260806160000_rpc_caller_check.sql` **1ファイルだけ**を見ていたので、
  後のマイグレーションで `CREATE OR REPLACE` して包み（`assert_can_act_for`）を
  外しても**古い定義を読んで緑のまま**だった。全マイグレーションを流した順に見て
  **最後の定義**を取るようにした（変異で確認済み）。
- **`src/test/bookingErrors.test.ts` が `GB009` を「未来のコード」としてハードコード**
  していたので、実装した日に4件落ちた。`KNOWN_GUARD_CODES` に無いものを選ぶようにした。

## お客様の画面（第2段・2026-09-22）

カレンダーで**次回分の日を薄くして押せなく**し、その下に
「次回分のお支払いの確認後に、10月18日（土）以降のご予約ができるようになります」
を出す。**押す前に理由が分かる形**にするため（薄いだけだと店へ問い合わせになる。
2026-09-03 に GB007 で実際に起きた）。

読み口は `get_my_next_cycle_payment_gate`（1つの日付だけ）。
**画面で暦を組み立てない**——組み立てると GB009 とズレる。
読めなければ null＝何も止めない（最終判定は DB が持っている）。

### 🔴 「その日を選べるか」の規則を1ファイルに集めた

`src/lib/bookingCalendarDay.ts`（`isDayUnselectable`）。

`CustomerBooking` の `<Calendar disabled={...}>` に**6つの規則が直書き**されていて、
足すたびにあのファイルが膨らみ（行数の上限まであと2行だった）、
**規則としてのテストが1つも書けなかった**（画面を描かないと確かめられない）。
実際 2026-09-21 に「満枠の日を押せなくする」が**一度も効かないまま**出荷されて
本番で指摘されている（`mem/features/booking-calendar-day-full.md`）。

移したことで、押せない理由が1ファイルに収まり、素のテストで確かめられるようになった
（`src/test/bookingCalendarDay.test.ts`）。**新しい規則を足しても画面は1行も増えない。**
⚠️ `disabled` に規則を書き戻さないこと。理由が2か所に分かれて片方だけ直す事故が起きる。

## 🔴 出した直後に本番で事故った（2026-09-22・同日）

宗本さんが設定画面でスイッチを押したが、**ONにならないように見えた**。

> オンにできない

**実際は ON になっていた。** 画面の表示だけが嘘をついていた。

原因は `src/lib/tenantColumns.ts` の `TENANT_OPTIONAL_COL_GROUPS` に
**新しい2列を足し忘れていた**こと。`Tenant` 型・設定画面・マイグレーションは
揃っていたのに、`useTenant` が引く列の一覧にだけ入っていなかった。

症状のたちが悪さ:

| | |
|---|---|
| スイッチを押す | DB は**本当に更新される**（トーストも「保存しました」） |
| 読み直す | その列が無いので undefined → `=== true` が false |
| 画面 | スイッチは **OFF のまま戻る**。店主には「ONにできない」としか見えない |
| 実際 | **ONになっている**。お客様の予約が止まり始めている |
| さらに | カルテのスイッチも同じ列を見ているので**出ない＝解除する手段が無い** |

本番の実害: 在籍39人中**38人に制限がかかり、翌日から12人・2週間で18人が
予約できない**状態だった。しかも古いアプリは GB009 を知らないので、
お客様には「アプリを更新してください」としか出ない。

気づいて即 OFF に戻した（`still_blocked = 0` を対照つきで確認済み）。
`next_cycle_payment_required_since` は**残してある**（次に ON にするとき上書きされる）。

### 見張りを足した

`src/test/tenantColumns.test.ts`:
**`Tenant` 型が宣言したカラムは、すべて `TENANT_COL_VARIANTS[0]` に入っていること。**

`tenantColumns.ts` の冒頭コメントは「書き漏らすと『設定画面には出るのに読めない』
というズレが静かに入る」と**まさにこれを警告していた**が、見張るテストが無かった。
例外（`invite_code` は専用 RPC で読む）は理由つきで一覧に書く決まりにした。

**この種類のバグは、新しいテナント設定を足すたびに起きうる。**
落ちたときのメッセージに直し方（`TENANT_OPTIONAL_COL_GROUPS` の末尾に足す）を書いてある。

## 残っていること

- **いま本番は OFF**（上の事故で戻した）。入れ直す順番は
  Publish → iOS ビルド（1.7.5）→ 公開を確認 → 設定で ON。
  ネイティブの画面なので、**マージしても Publish してもお客様の端末には届かない**
  （`mem/ops/release-signal.md`）。先に ON にすると、アプリのお客様には
  日付が薄くならないまま「アプリを更新してください」とだけ出る。
- 未入金の方を店が一覧で見つける導線は無い（カルテを開けば分かる）。
  対面でその場で押す運用なので当面は足していない。
