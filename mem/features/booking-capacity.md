# 同時に受けられる予約数（tenants.booking_capacity）

## 概要（2026-08-01〜）

それまでの重複防止は「テナント内で時間が重なる予約が**1件でもあれば拒否**」だった。
つまり **1テナント＝同時に1予約** が暗黙の前提で、

- ベッドが2台ある
- 施術者が2人いる
- 打席・個室が複数ある

といった「同時に複数受けられる店」を表現できなかった。パーソナルジム（1対1）では
正しい前提だったが、ストレッチ・鍼灸・エステなど複数ベッドが普通の業種へ広げる際の
構造的な障害になっていた（`mem/ops/vertical-fork.md`）。

`tenants.booking_capacity`（既定1）を追加し、**重なっている予約の件数**を数えて
`件数 >= capacity` で拒否するようにした。

**既定1なら「1件でも重なれば拒否」＝従来と完全に同一の挙動**なので、既存の全店に影響はない。
設定画面（ジム設定 → 営業時間）の「同時に受けられる予約数」で店ごとに変更する。

## ⚠️ 仕組みを入れただけでは足りなかった（2026-08-02 追記）

上記のとおり**仕組みとしては1人運営でも複数人運営でも表現できる**が、
2026-08-02 に本番DBを照会したところ、**14テナント全部が `booking_capacity = 1` のまま**だった。
`tenant_members` に `trainer` ロールのレコードも0件（全店オーナー1アカウントのみ）。

つまり「複数人で回している店がアプリ上は1人運営に見える」状態が起こりうる。
そういう店では:

- お客様の予約画面で、**実際は空いている枠が「満枠」と出る**
- トレーナーが代理予約しようとすると「すでに予約が入っています」で弾かれる

となり、**「このアプリは同時対応に非対応」と誤解されて終わる**。設定が奥にあり、
既定が安全側の1で、しかも**誰も設定の存在を知らない**のが原因。
（この件は「アプリ上のアカウント数」では検知できない。オーナー1アカウントで
複数スタッフの予約を管理している店は、DBを見ても1人運営と区別が付かない）

そこで**設定に気づく経路を3つ**入れた:

| 経路 | 対象 | 実装 |
|---|---|---|
| 開店時に必ず聞く | これから開く店 | オンボーディング step2（営業時間と同じ画面）。`Onboarding.tsx` |
| 詰まった瞬間に案内する | すでに動いている店（トレーナー操作） | 代理予約が弾かれたとき、`capacity <= 1` なら設定の場所を書いたトーストを出す。`TrainerSchedule.tsx` |
| 取りこぼした需要を見せる | すでに動いている店（**お客様の自己予約**） | ダッシュボードに今後のキャンセル待ちを出す。`capacity <= 1` なら設定の案内も添える。`TrainerDashboard.tsx` |

### 3つ目が要る理由（1・2 では届かない経路がある）

**予約の大半はお客様の自己予約**で、その経路では満枠の枠がグレーアウトされるだけなので、
トレーナーは代理予約を試さない限り何も起きない。つまり 1・2 だけだと
**一番件数の多い経路で取りこぼしても店は永久に気づけない**。

一方で `booking_waitlist` には「入りたかったのに入れなかった人」がすでに溜まっている。
にもかかわらず**これを読むトレーナー画面がどこにも無く、データを捨てていた**。
ここを見せるだけで、キャンセル待ち機能そのものの価値も出る
（本当に満席の店にとっても「誰がどの枠を待っているか」は有用な情報）。

### 業種で既定値を決めようとしないこと

一時「業種ごとに正しい既定値を決める」方向で考えたが、**これは誤り**。
1人で回す店と複数人で回す店は**同じ業種の中に両方ある**（接骨院でもジムでもサロンでも）。
業種を知っても答えは出ないし、そもそもアプリ側が知る必要が無い。

**正しい形は「どちらでも正しく動き、実態と設定がずれていたら店が気づける」**こと。
上の3経路はそのための仕組みで、値そのものを推測して書き換えてはいない。

**既定値は1のままにしてある。** 「分からないから2にしておく」は、本当に1対1の店で
二重予約を通してしまい、お客様が来たのに対応者がいないという実害を生む。
安全側に倒したうえで、設定に辿り着ける導線を作るのが正しい形。

回帰テストは `src/test/bookingCapacityDiscovery.test.ts`。
**兄弟アプリ向けに、この2つの新文言は業種オーバーレイの対象**（「ジム設定」の部分が
「サロン設定」「スタジオ設定」等に変わるため）。プリセットに追加済み。

## 規則

| 対象 | 扱い |
|---|---|
| 通常予約（`bookings`） | 1件と数える |
| 体験予約（`trial_bookings`） | 1件と数える（実際にベッドと人を専有するため） |
| キャンセル済み | 数えない |
| **ブロック枠（`blocked_slots`）** | **capacity に関係なく店全体を塞ぐ** |

ブロック枠は休憩・私用・臨時休業に使うものなので、「ベッド1台分だけ休憩」という概念は持たない。
将来ベッド単位で埋めたくなったら `blocked_slots` 側に対象を持たせる別の工事になる。

同様に、トレーナーが**ブロック枠を作る**ときの事前チェックは capacity を使わない
（`TrainerSchedule.tsx`）。空きベッドがあってもブロックは店全体を閉めるので、
既存予約を巻き込む時間帯にはブロックを作らせない。

## 実装箇所

**DB（最終防衛・ここが権威）** — `supabase/migrations/20260801000000_booking_capacity.sql`
- `check_booking_overlap` トリガー: 重なりを `kind`（'booking' / 'block'）付きで集計し、
  `ブロックが1件でもある OR 予約の重なり >= capacity` で拒否。
  エラー文言は据え置き（capacity=1 のとき従来と1文字も変わらないようにするため）。
- `get_tenant_public` RPC: `booking_capacity` を追加で返す。
  公開ページ（体験予約・ドロップイン）が未ログインで候補枠を判定するのに必要。
- `CHECK (booking_capacity >= 1)`: 0 を入れると全予約が入らなくなり原因が分かりにくいため禁止。

**クライアント（事前チェックのUX）**
- `useBookings.checkSlotBlocked` … 第7引数 `capacity`（既定1）。`.some()` → 件数カウントに変更
- `CustomerBooking.tsx` / `TrialBooking.tsx` / `DropInBooking.tsx` の各 `isSlotBlocked`
- `TrainerSchedule.tsx` … 代理予約の判定にのみ capacity を渡す（ブロック作成には渡さない）
- `tenantColumns.ts` … 列が読めない環境では **1**（安全側）にフォールバック

## 落とし穴

- **クライアント側だけ直しても意味がない。** 二重予約を実際に防いでいるのは DB トリガーだけで、
  フロントの判定は全て事前チェックのUXに過ぎない。逆に、フロントを直し忘れると
  「画面上は空きに見えるのに予約するとエラー」になる。両方揃えること。
- `blocked_slots` への INSERT は `check_booking_overlap` を通らない（トリガーは
  `bookings` / `trial_bookings` のみ）。ブロックと予約の衝突チェックはクライアント側だけ。
- capacity を**下げる**とき、既にその時間に capacity を超える予約が入っていても
  既存予約は消えない（トリガーは INSERT のみ）。表示上は定員超過のまま残る。

## 未対応（次の工事）

- **どのベッド／誰が担当か**は持っていない。capacity は「同時に何件受けられるか」だけで、
  予約とリソースの紐付け（指名・個室指定）はできない。
  `bookings` にスタッフ列／リソース列を足す別の設計が要る。
- 曜日別の capacity（平日2・土日3 など）も未対応。`operating_hours` が
  `{start, end}` 1組しか持っていない制約と同じ根を持つ。
