# 回数の数え方（サイクル窓と「実効サイクル」）

## 概要
「今回の何回目か」を出すロジックは `src/lib/courseProgress.ts` に集約。
表示先は2系統ある。

| 表示 | 入口 | ファイル |
|---|---|---|
| 予約チップの「2/4」 | `getBookingProgressIndex` | `TrainerSchedule` / `WeekTimelineView` / `TrainerDashboard` / `CustomerBooking` |
| プロフィールの「予約済み 2/4・利用期間 7/28〜8/29」 | `computePlanUsage` | `PlanUsageCard`（`src/lib/planUsage.ts`） |

**この2つは必ず同じ窓で数えること。** 別々の窓を使っていたのが下記の不具合。

## 暦窓（getCycleWindow）と実効サイクル（resolveEffectiveCycle）
- `getCycleWindow` は起算日の**応当日ベースの暦窓**。起算日 6/30・1ヶ月なら
  `[6/30, 7/31)` `[7/31, 8/31)` …（応当日 7/30 は前サイクルの最終日）。
- `resolveEffectiveCycle` はそこに**ジムの運用**を重ねたもの。
  「回数を使い切ったら、期限の終わりを待たずに次のルーティンが始まる」ため、
  窓内の有効予約が上限を超えたら (上限+1)回目の予約日を新しい起算日にして窓を引き直す。
  猶予（graceDays）で前サイクルへ繰り入れた分（`lent`）は今サイクルの消化に数えない。
  ロールするのは**新ルーティンの1回目の日が実際に来てから**（未来の予約では窓を動かさない）。

## 2026-07: 応当日をまたぐとチップの回数が1に戻る不具合
起算日 6/30・月4回・猶予OFFのお客様で、8/7 の予約チップが **1/4**（正しくは 2/4）と表示された。
プロフィール側は「予約済み 2/4・利用期間 7/28〜8/29」と正しく出ており、画面間で食い違っていた。

実データ: 6/30, 7/8, 7/13, 7/21, **7/28**, 8/7。

原因は `getBookingProgressIndex` だけが**暦窓**で数えていたこと。
暦窓 `[6/30, 7/31)` には5件入るので、5件目の 7/28 は
「`((5-1) % 4) + 1 = 1`」という剰余で新ルーティンの1回目として出せていた。
しかし 8/7 は次の暦窓 `[7/31, 8/31)` に落ちるため件数が振り出しに戻り、
**7/28 から新ルーティンが始まっている事実が失われて**また 1 になっていた。
剰余のごまかしは1つの暦窓の中でしか成立しない。

**対処**: `getBookingProgressIndex` も `resolveEffectiveCycle`（＝`computePlanUsage` と同じ窓）で
数えるようにした。7/28 でロールして窓が `[7/28, 8/29)` になるため、8/7 は素直に2件目になる。
猶予の繰入数も `graceLentToPrevCount` を自前で呼ぶのをやめ、`resolveEffectiveCycle` が返す
`lent` を使う（繰入の判定を2箇所で持たない）。剰余は、同日に上限を超える予約が入って
窓を引き直せない場合の保険として残してある。

## 落とし穴
- **回数の表示を足すときは `resolveEffectiveCycle` を通す。**
  `getCycleWindow` を直接使うと、応当日をまたいだ瞬間にカウントが1に戻る。
- チップ側の呼び出しは `resolveCycleMonths` / `resolveGraceDays` を必ず渡すこと
  （`resolveGraceDays` は `profiles.grace_enabled=false` のお客様で0を返す）。
- 起算日より前の予約はどの窓にも入らないので `getBookingProgressIndex` は `null` を返す
  ＝チップが出ない。トレーナーが起算日をリセットした場合の過去分がこれに当たる（仕様）。
- 回帰テストは `src/test/courseProgress.test.ts` の
  「getBookingProgressIndex × 使い切り後のロール」。本番の実データをそのまま置いてある。

## 2026-09-24: 期間は1回目の日に引き直すのに、回数は元の暦窓で数えていた

宗本さん（顧客詳細のスクリーンショット）「これカウントの仕方おかしい」。

起算日 9/17・月4回・猶予OFF・予約 10/3, 10/10, 10/24 のお客様で、カードが
**「利用期間 10/3〜11/3」なのに「予約済み 2/4・2回予約可能」**と出ていた。

`computePlanUsage` は `anchorToFirstBooking: true` で、期間を「実際の1回目の日から」に
引き直して見せる。ところが `finalizeWindow` は**期間の日付だけ**引き直し、回数は
元の暦窓 `[9/17, 10/18)` で数えたまま返していた。10/24 は表示している期間の中なのに数えない。

**対処**: 引き直すときは、1回目の日を起算日とみなして `resolveEffectiveCycle` を
解決し直す（＝起算日が1回目の日に合っていた場合と同じ結果。ロール・猶予も同じ規則で働く）。
Deno 移植（`supabase/functions/_shared/cycle.ts`）も同じ（`cyclePortParity.test.ts`）。

- 本番の全カード（42件）を修正前後で再計算して、変わったのは**2件だけ**・どちらも正しい方へ:
  - 上のお客様: 2/4 → **3/4・残り1**
  - 起算日 6/6 のまま・期間 9/5〜10/5 に4件のお客様: 3/4 → **4/4（使い切り）**。予定表のチップ（1〜4）と揃った
- ⚠️ `allow_overflow=false` のプランは**引き直さない**（DB の GB004 は暦窓で数えて拒否する。
  表示もその窓にして、期間・回数・DB を揃える）。本番には該当プランが無い（2026-09-24 時点）
- 起算日固定（pinned）は従来どおり引き直さない

### まだ残る食い違い: 起算日が1回目の日とずれたまま保存されているお客様

上のお客様は**起算日が 9/17 のまま**（9/13 に設定された。10/3・10/10 の予約はその前から
入っていたので、「最初の窓の1回目で起算日を合わせる」自動調整が一度も走らなかった）。
予定表のチップ（`getBookingProgressIndex`）と DB（`plan_cycle_window`）は保存された起算日の
暦窓で数えるので、猶予OFFのこのお客様では 10/24 が「次の期間（10/18〜）の 1/4」になり、
カード（3/4）と食い違う。10/18 を過ぎるとカードの期間も 10/24 起点に変わる。
**起算日を 10/3 に直せば、カード・チップ・DB がすべて揃う**（テストで確認済み）。

→ 2026-10-15 にチップ側を直した（下の節）。起算日がずれたままでも、カードとチップは揃う。
DB（`plan_cycle_window`）は今も保存された起算日の暦窓のまま。

見張り: `src/test/planUsageAnchoredCount.test.ts`（7件。日付は本番の実データ、名前は持たない）。
変異3件（クライアントを元に戻す／Deno 側を元に戻す／allow_overflow=false でも引き直す）がすべて赤。

## 2026-10-15: 間が空いたあとの区切りを、1回目の日ではなく起算日の応当日で切っていた

宗本さん（予定表のスクリーンショット）「次回の1回目のトレーニング日が10/22やから11/22までで
4回なのに11/12の予約がまた1回目ってどういうこと？ 1回目から自動的に1ヶ月間で計算するようにしろ」。

起算日 10/6（固定なし）・月4回・猶予OFF・予約 10/22, 10/29, 11/5, 11/12 のお客様で、
予定表のチップが 10/22=1/4, 10/29=2/4, 11/5=3/4, **11/12=1/4**（正しくは 4/4）。
カードは「10/22〜11/22・4/4」で、画面どうしでも食い違っていた。

原因は2つ重なっていた:
1. チップ（`getBookingProgressIndex`）は保存された起算日の暦窓 `[10/6, 11/7)` `[11/7, 12/7)` で
   数えていた。11/12 は2つ目の窓の1件目になる（上の「まだ残る食い違い」そのもの）
2. カードの `anchorToFirstBooking` も、引き直すのは**最後の区切り1つだけ**。途中の区切りは
   応当日で切るので、期限が切れて間が空くたびに、次の区切りの1回目が窓の途中に来てずれる

**対処**: `resolveEffectiveCycle` に `reanchorRoutines` を足した。区切りを順に進める**途中でも**、
区切りの最初の予約（猶予繰入を除く）が区切りの開始日より後なら、その日を起算日として引き直す。
チップは `reanchorRoutines: true`、カードは `anchorToFirstBooking: true`（これも同じ引き直しを含む）で、
両方が同じ規則になる。Deno 移植（期限のお知らせ）も同じ（`cycle.ts` の `computeSubscriptionUsage`）。

- 引き直すのは**その1回目の日が referenceDate までに来ている場合だけ**。未来の予約で先回りして
  動かすと、猶予で前の区切りへ繰り入れた予約が区切りから外れて数えられなくなる
- 起算日固定（pinned）・`allow_overflow=false` は引き直さない（従来どおり）
- 猶予の既存テスト2件は、データの1回目を起算日の当日（6/4）に寄せた。1回目が起算日より後
  （6/6）だと、新しい規則では期限が 7/6 まで延びて「猶予」の場面にならないため。
  1回目が 6/6 の場合の新しい結果は別のテストで押さえてある
- 本番の全お客様（50人・チップ583個）を修正前後で再計算して、変わったのは:
  - チップ3個。どれも「1回目から1ヶ月」に揃う方向:
    - 起算日 5/18 のお客様: 6/23 から始まった区切り（6/23, 6/30, 7/7, 7/21）の
      7/21 が 1/4 → **4/4**、次の 7/27 が 2/4 → **1/4**（今回と同じ型）
    - 起算日 6/6・猶予7日のお客様: 10/3 が「4/4（前回分）」→ **4/4**
      （9/5 から始まった区切りは 10/5 までなので、猶予に頼らず素直に入る）
  - カード3枚。どれも今の区切りに予約が1件も無いお客様。画面は日付ではなく「1回目のご予約から」
    （`periodPending`）なので見た目は変わらない（裏の暦窓の日付が数日ずれるだけ）。期限のお知らせも
    `periodPending` は送らない
- ⚠️ Deno 移植の変更は、Lovable に `push-period-reminder` をデプロイしてもらうまで本番で動かない
  （`mem/ops/edge-function-deploy.md`）。デプロイ前は、区切りの境目が動いたお客様だけ
  お知らせの日付がカードと数日ずれうる

見張り: `src/test/cycleReanchorRoutines.test.ts`（9件。日付は本番の実データ、名前は持たない）と
`courseProgress.test.ts` の猶予の2件。変異6件（チップで引き直さない／途中の区切りを引き直さない／
未来の1回目でも引き直す／pinned でも引き直す／allow_overflow=false でも引き直す／Deno 側を戻す）がすべて赤。
