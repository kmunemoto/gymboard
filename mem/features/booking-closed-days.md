# その日の受付を止める（1日の上限人数＋ワンタップ受付停止）

2026-09-01 に入れた。実店舗（宗本さん）の要望:

> 1日に見れる人数に制限をかけたい。その日が上限に達したら、枠が空いていても受付を止める。
> 枠を1つずつブロックするのは面倒なので、その日をワンタップで受付停止・ワンタップで解除したい。

## 止め方は2つ、答えは1つ

| | 何が起きるか | 戻し方 |
|---|---|---|
| 手で閉める（`booking_closed_days`） | その日をワンタップで閉める | 同じボタンをもう一度押す |
| 上限に達する（`tenants.daily_booking_limit`） | **会員予約**の件数が上限に届いた瞬間、自動で閉まる | 上限を上げるか、その日の予約を減らす |

どちらも**体験・ドロップインには効かない**（下記）。

お客様から見ればどちらも同じ「受付終了」なので、**公開RPC `get_tenant_closed_days` が
両方まとめて返す**。画面側に規則を組み立てさせない（組み立てさせると、直し忘れて
「空きに見えるのに予約できない」が静かに残る）。

## 🔴 店側の代理予約には効かない

GB003 / GB004 / GB006 と同じ非対称。「今日はもう受けない」と決めたあとで常連さんを
1人だけ足すのは店の裁量として残す。止まるのは **お客様の自己予約** と
**公開の体験・ドロップイン予約** だけ。

会員予約のガードは `auth.uid() = NEW.user_id` のときだけ働く。

## その日だけ上限を外す（`booking_uncapped_days`・2026-09-20）

> 今入れられる予約を1日4人までにしてて、4枠予約が入ったら受付をやめる様にしている
> のですが、ベースはそれで特定の日はそのルールを適応しない様にしたい。

**予定表のオレンジ「上限に達しました」をタップ → その日だけ上限なし。もう一度タップで戻る。**
外した日は**無制限**（人数の指定はしない）。

それまでオレンジは押せない札だった（「解除したのにまた閉まる」を避けるため）。
解除の実体を `booking_uncapped_days` に持たせたので、押しても閉まり直さない。

⚠️ 1回目のタップは既に「受付を止める」に使われている。3状態を1つのボタンで回すと
戻すのに3回押すことになるので、**オレンジからだけ**外せるようにした。
上限に達していない日は上限が邪魔をしていないので、外す必要が無い。

### 🔴 手で止めた日のほうが強い

`tenant_day_closed` は**手動を先に**見て、そのあと上限なしを見る。
順番を入れ替えると「今日はもう受けない」と決めた日が上限なしの指定で**勝手に開く**。
画面側（`DayReceptionToggle`）の分岐も同じ順番に揃えてある。

### 外すのは1日の上限だけ

| | 上限を外した日 |
|---|---|
| 1日の人数の上限 | **見ない** |
| 営業時間・定休日・予約の締切 | 効く |
| 同時受入数・時間ブロック・担当のシフト | 効く |
| プランの回数上限・受付しない時間帯 | 効く |

数え方（`tenant_day_booking_count`）は変えていない。上限なしの日でも件数は今までどおり
数える（「n/4人」の表示に使う）。変えたのは**その件数で閉めるかどうか**だけ。

### 本番へ適用した記録（2026-09-20）

3段構え。**7パターンすべて設計どおり**（`RAISE EXCEPTION` で全部ロールバック済み）。

```
(1) 9/23 上限を外した            = tenant_day_closed false  ← 開いた
(2) 9/22 手で止めた日＋外した(対照)= true のまま            ← 順番が効いている
(3) 9/26 外していない(対照)       = true
(4) 公開RPC: 9/23 が一覧から消え、手動の日はそのまま残る
(5) 会員の自己予約 x 外した日     = 入った
(6) 会員の自己予約 x 外さない日(対照)= 断られた [GB007]
(7) 外した日 x 埋まった枠(対照)   = 断られた（同時受入数は生きている）
```

残骸0件。`delete_my_gym` の消し込みにも足した（36→37件。本番の実物と突き合わせてから写した）。

番人は `src/test/bookingUncappedDays.test.ts`（20件）。変異7パターンが赤になることを確認済み。

## 🔴 体験・ドロップインは仕組みから完全に外れている（2026-09-01）

宗本さんの指示:「体験予約はこのシステムの例外にします。体験予約は上限なく受け付けます」。
数え方も確認済み:「数えない（仕組みから完全に外す）」。したがって:

- 受付を止めた日でも、体験は入る（`trial_bookings` にトリガーは無い）
- 上限に達した日でも、体験は入る
- **体験は1日の人数にも数えない。** 上限5人の日に体験が3件入っても、会員はまだ5人まで
  取れる（合計は5人を超える）

ドロップインも一緒に外れている。ドロップインは体験と**同じ `trial_bookings` テーブル**に
あり（`booking_kind` で区別）、画面側は両者を区別せず `user_id === "trial-guest"` として
扱っている。DB だけ `booking_kind` で分けると、画面の人数と DB の判定がずれる——このリポジトリで
最も避けたいズレ（画面は空きと見せるのに DB が拒否する）。本番のドロップインは全テナントで
0件なので、テーブルごと外すほうが安全。分けたくなったら `useBookings` に `booking_kind` を
運ばせてから、DB と画面を同時に変えること。

公開の体験ページ・ドロップインページは受付終了を**一切見ていない**。DB が止めないのに
画面だけ止めると、予約できるはずの枠が消えるため。

## 数え方

`status <> 'キャンセル済み'` の **bookings だけ**。

- 🔴 **「同日キャンセル済み」（消化扱い）は数える。** 予定表に枠として残り続けるものを
  空きとして数えると、受付終了にしたはずの日がひとりでに開く。
- ブロック枠（`blocked_slots`）は数えない。予約ではないため（休憩を入れただけで
  受付が止まるのはおかしい）。
- 体験・ドロップイン（`trial-guest` の行）は数えない（上記）。
- 予定表の一覧（`getDayBookings`）は「同日キャンセル済み」を**表示から**外している。
  人数を数えるときにそれを使い回さないこと。`useDayReception` の `bookedCountOn` を通す。

## 上限は毎日おなじ1つの数字

曜日別には持たない（2026-09-01 にそう決めた）。曜日で変えたい日は、予定表から
その日を手で止めれば同じことができる。設定を増やすより、1つの数字＋ワンタップのほうが軽い。

## どこにあるか

- 予定表の**日付ヘッダ**（週間・日別の両方）に1タップのスイッチ。
  🔴 **週間ビューが既定**なので、`WeekTimelineView` にも渡すこと。
  日別だけに入れて満足しかけた（画面を出して数えるまで気づけなかった）。
- 上限の数字は ジム設定 → 予約のルール（回数の制限・受付しない時間帯の隣）。
  営業時間カードではない。あちらは「何時から何時まで開けるか」で目的が違う。

## 列が読めない環境

`daily_booking_limit` の既定は **null（上限なし）**、`closedDays` の読み込み失敗は
**空配列（閉まっている日は無い）**。逆に倒すと、マイグレーション未適用の環境で
**全店の受付が勝手に止まる**。最終判定は DB のトリガー（GB007）が持っているので、
画面側が緩くても抜け道にならない。

## 🔴 古いアプリには「空きに見えるのに断られる」（2026-09-03）

出荷後にお客様から店のチャットに届いた:

> 9/13 13:45 から予約しようとしてるんですが、「予約に失敗しました」と表示され予約できず…
> ちなみに他の日時は予約できたので、この部分だけの不具合かもしれません。

不具合ではなく、**そのお客様のアプリが古かった**。この機能（GB007）を知らないアプリは
上限に達した日の枠を**「空き」として見せ**、送信して初めて DB に断られる。

これは仕組み上どうしても起きる。DB は全員に同時に効くが、アプリは各自が更新するまで
古いままだからだ。**新しい予約のガードを足すたびに、更新していない人に同じことが起きる。**

### 手当て（PR #379）

案内を変えた。予約のガードはすべて `GB0xx` を持つので、**このアプリが知らない `GB0xx` が
返ってきた ＝ サーバーの規則のほうが新しい ＝ アプリが古い**、と言い当てられる。
推測ではなく、コードそのものが証拠になる。→ `src/lib/bookingErrors.ts`

⚠️ **この案内は「これから配る版」にしか入らない。** すでに古い版を使っている人には届かない。
効くのは次に規則を足したとき。今回のお客様は救えていない。

### 残っている手（やっていない）

起動時に最低バージョンを見て更新を促す。確実だが作る量が多いので、同じ問い合わせが
繰り返されるようなら検討する。

## 当日が上限で埋まっていても、押して空き状況だけは見せる（2026-09-05）

実店舗の要望（宗本さん）:

> 一日四枠までに設定して四枠以上取れないようにしたら、四枠入っている日は日にちが
> グレーになって押せなくなる。それが当日であってもグレーで押せなくて、何時が空いてるか
> 分からなくなる。
>
> **当日の日付を押した時**でお願い。**アプリから当日の予約の変更はできません。**
> **その日の状況を見てお客さんはお店に連絡するシステム**です。

⚠️ 最初、これを「予約変更のときに開ける」と読み違えて作った。**当日はアプリから
予約も変更もできない**（締切済み）ので、変更フローは走らない。**押して見るだけ**が正しい。

### 開けるのは「当日 × 上限で埋まった日」だけ

| 種類 | `ClosedDay.manual` | 当日 | 先の日付 |
|---|---|---|---|
| 上限に達した（4/4） | `false` | **押せる（見るだけ）** | 押せない |
| 店がワンタップで止めた | `true` | 押せない | 押せない |

- **手で止めた日**は店が「今日はもう受けない」と決めた日。開けると意図に反する
- **先の日付**まで開けると、店が上限で止めた日に問い合わせが増える。これも意図に反する
- **当日**はそもそも締切済みで予約も変更もできないので、押せても「見るだけ」以上のことは
  起きない。お客様は空き時間を見て**店に電話する**

### 見せ方

- 枠は出す（0件にしない）。0件だと「何時が空いてるか分からない」という元の不満に戻る
- 🔴 **1枠も押せない**（`available: !selectedDayViewOnly && ...`）。
  DB も GB007 で断るので、押せる見た目にすると「押したのに断られる」になる
- 空き枠は「空き」と分かるように出す（`viewOnlyOpen`。締切済みの当日と同じ見た目）
- 「本日の受付枠は埋まっています／ご相談はお店へ直接ご連絡ください」を出す（5言語）

判定は `isDayHardClosed`（日付ごと塞ぐ）と `isDayViewOnly`（押せるが見るだけ）の2本。

### 見張り

`src/test/bookingClosedDays.test.ts`。変異4種で赤になることを確認済み:

1. 手で止めた当日まで開ける
2. 先の日付の上限まで開ける
3. 枠を押せるようにしてしまう（DB に断られる）
4. 空き枠を「満枠」に潰す（元の不満に戻る）

⚠️ `bookingBlockedWindows.test.ts` が `viewOnlyOpen` の式を丸ごと固定していたので緩めた。
見るべきは **`&& !displayBlocked` が残っていること**＝受付しない帯が「空き」に戻らないこと。
左側の条件が増えるのは想定内。緩めたあとも、`!displayBlocked` を外す変異で赤くなる。
