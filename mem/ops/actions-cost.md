# GitHub Actions の枠と費用（全アプリ共通）

2026-08-10、ストレッチボードで**アカウントの Actions 枠を使い切って全ビルドが止まった**。
症状が「ワークフローのバグ」にしか見えず、切り分けに時間を使ったので記録する。

このメモの対象は**ジムボード自身ではない**。ジムボードは public なので Actions は無料で、
枠切れの影響を受けない。困るのは **private の兄弟アプリ**（Lovable 由来の
`project-<uuid>` 群など）で、そちらに効く話をここに集約する。

## 1. 枠切れの症状（これが一番分かりにくい）

枠を使い切ると、ジョブはこう落ちる。

```
conclusion: failure          ← startup_failure ではない
ジョブの所要時間: 5秒前後
steps: []                    ← ステップを1つも実行していない
runner_id: 0, runner_name: ""← ランナーが割り当てられていない
ログ: HTTP 404               ← そもそも存在しない
```

**ワークフローの構文エラーだと思って延々と直しにいくことになる。** 構文エラーなら
`startup_failure` になってステップ一覧が出るので、そこで区別できる。

### 切り分けの決め手

**public リポジトリと private リポジトリを、同じ時刻で比べる。**

```
ストレッチボード（private）  15:04 以降  全て5秒で失敗
ジムボード      （public）   15:02-15:04 CI 正常成功（2分1秒）
```

同一アカウント・同一時刻で、違いは公開設定だけ。ここまで出れば確定できる。
`ubuntu-latest` のワークフローも同時に落ちるので、「macOS 固有の問題」ではない。

## 2. 課金モデル（ここを取り違えると読み違える）

- 含まれる分（Free/Pro は月2,000分）は**アカウント単位**。**すべての private
  リポジトリで分け合う**。このアカウントは25本中22本が private
- **public リポジトリは無料**。含まれる分を消費しない
- OS ごとの倍率: Linux 1倍 / Windows 2倍 / **macOS 10倍**
- 既定では Actions の予算が **$0** に設定されており、超過分は**課金されず
  ブロックされる**。上げれば即座に復旧する

### iOS ビルド1回の重さ

実測（ストレッチボード run #14、成功してアップロードまで到達した回）:

```
全体 279秒（4分39秒）→ 含まれる分の消費 50分（10倍換算）
```

**月2,000分は、成功する iOS ビルド20回で尽きる。** リリースのたびに数回回すことを
考えると、private のまま iOS を回し続けるなら枠は必ず足りなくなる。

### 実費（超過してから）

- macOS: 1分 $0.08 → **iOS ビルド1回 約 $0.40〜0.80**
- Ubuntu: 1分 $0.008 → CI 1回 約 $0.02

**10倍換算は「含まれる分」の話で、実費は実時間 × OS 単価。** 課金され始めれば
iOS ビルドは1回40〜80円で、金額としては安い。

## 3. 効果の実測（過度な期待をしないこと）

ストレッチボードの iOS ワークフローで、Swift Package の解決と npm をキャッシュした。
**アップロードを除いた同条件**で比較する（dry run を使って測定した）。

```
キャッシュ無し  241秒
キャッシュ有り  218秒     → 23秒（約10%）短縮
```

ステップ単位では、

```
Swift Package の解決   88秒 → 35秒（-53秒）
ただしキャッシュ復元に        +16秒
npm install            26秒 → 20秒（-6秒）
setup-node のキャッシュ復元   +9秒
アイコン生成           13秒 →  2秒（-11秒、~/.npm が温まるため）
```

**「解決が88秒だから88秒浮く」とはならない。** 復元自体に時間がかかるうえ、
macOS ランナーのディスクは遅い。**npm のキャッシュはほぼ収支ゼロ**（復元コストが
節約分をほぼ食う）。archive 自体のばらつきが59〜89秒あるので、1回の測定の
不確かさもこの差と同程度ある。

つまり **分の最適化に工数をかけて回収できる金額は1回あたり20〜30円**。
実装と検証に半日かける価値はない。

## 4. 実装上の罠（どちらも実際に踏んだ）

キャッシュを入れるなら、この2つは避けられない。

### 罠1: キャッシュ復元は `npx cap add ios` より後に置く

`actions/cache` は**復元先の親ディレクトリを作る**。`ios/App/SourcePackages` を
`cap add ios` より前に復元すると `ios/` が既に存在することになり、

```yaml
- run: npx cap add ios || true
```

が**プロジェクト生成を丸ごと飛ばす**。この後のステップが軒並み意味不明な顔で落ちる。

### 罠2: `-clonedSourcePackagesDirPath` は resolve と archive の両方に渡す

既定の置き場所（DerivedData 配下）はパスにハッシュが入るのでキャッシュできない。
固定するには `-clonedSourcePackagesDirPath` を渡すが、**片方だけだと archive が
既定の場所で解決し直す**。

キャッシュが効かないまま時間だけ戻り、**「なぜか遅い」以外の症状が出ない**。
テストで両者を突き合わせておくとよい。

## 5. 結論（効果の大きい順）

1. **public にする。** Actions が無制限に無料になり、枠の管理そのものが要らなくなる。
   効果が桁違いで、しかも無料。ただし**履歴に鍵が入っていないか**を先に確認すること
   （現在のファイルだけ見ても足りない。一度でも入っていれば公開される）
2. **予算を $0 から上げる。** 上限であって前払いではない。使わなければ請求は出ない。
   アラートを50%あたりに置いておくと、壁にぶつかる前に気づける
3. **`concurrency` を置く。** リリース経路は同時に2本走らせない。ただし
   `cancel-in-progress` は付けないこと。アップロード中に打ち切ると App Store Connect
   側に中途半端な配信が残りうる
4. **キャッシュは入れてもよいが、10%程度と見込むこと。** 待ち時間の短縮としては
   意味があるが、費用対効果で正当化はできない

## 6. ワークフロー変更を検証するときの dry run

キャッシュのように**ワークフロー自体**を変更したとき、検証のたびに
App Store Connect へビルドが積み上がる。`workflow_dispatch` に入力を足して、
**アップロードだけ**を飛ばせるようにしておくと測定が楽になる。

```yaml
on:
  workflow_dispatch:
    inputs:
      dry_run:
        type: boolean
        default: false
```

署名・アーカイブ・export は本番と同じ経路を通るので、これで十分検証できる。
⚠️ 既定を `true` にしないこと。「リリースしたつもりで上がっていない」が起きる。
既定値と、条件を付けたステップがアップロード関連だけであることはテストで固定する。
