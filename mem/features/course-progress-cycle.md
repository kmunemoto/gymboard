# 回数の数え方（サイクル窓と「実効サイクル」）

## 概要
「今回の何回目か」を出すロジックは `src/lib/courseProgress.ts` に集約。
表示先は2系統ある。

| 表示 | 入口 | ファイル |
|---|---|---|
| 予約チップの「2/4」 | `getBookingProgressIndex` | `TrainerSchedule` / `WeekTimelineView` / `TrainerDashboard` / `CustomerBooking` |
| プロフィールの「予約済み 2/4・利用期間 7/28〜8/29」 | `computePlanUsage` | `PlanUsageCard`（`src/lib/planUsage.ts`） |
| ホームの「次回の予約・今回 2/4回目」 | `getNextBookingOrdinal`（中身はチップと同じ） | `CustomerHome` |
| レポートの期間（月次レポート・部位バランス・ホームの「今回のレポート」） | `reportPeriodAt`（`src/lib/reportPeriod.ts`） | `CustomerMonthlyReport` / `MuscleBalanceRadar` / `CustomerHome` |
| 予約カレンダーの利用期間の帯・説明・日を選んだときの一言 | `calendarPeriods` / `periodDayHint` / `repeatPeriodBreak`（`src/lib/calendarPeriod.ts`） | `CustomerBooking`（`src/components/booking/CalendarPeriod.tsx`） |

**これらは必ず同じ窓で数えること。** 別々の窓を使っていたのが下記の不具合。

## 暦窓（getCycleWindow）と実効サイクル（resolveEffectiveCycle）
- `getCycleWindow` は起算日の**応当日ベースの暦窓**。起算日 6/30・1ヶ月なら
  `[6/30, 7/31)` `[7/31, 8/31)` …（応当日 7/30 は前サイクルの最終日）。
- `resolveEffectiveCycle` はそこに**ジムの運用**を重ねたもの。
  「回数を使い切ったら、期限の終わりを待たずに次のルーティンが始まる」ため、
  窓内の有効予約が上限を超えたら (上限+1)回目の予約日を新しい起算日にして窓を引き直す。
  猶予（graceDays）で前サイクルへ繰り入れた分（`lent`）は今サイクルの消化に数えない。
  ロールするのは**新ルーティンの1回目の日が実際に来てから**（未来の予約では窓を動かさない）。

## 2026-07: 応当日をまたぐとチップの回数が1に戻る不具合
起算日 6/30・月4回・猶予OFFのお客様で、8/7 の予約チップが **1/4**（正しくは 2/4）と表示された。
プロフィール側は「予約済み 2/4・利用期間 7/28〜8/29」と正しく出ており、画面間で食い違っていた。

実データ: 6/30, 7/8, 7/13, 7/21, **7/28**, 8/7。

原因は `getBookingProgressIndex` だけが**暦窓**で数えていたこと。
暦窓 `[6/30, 7/31)` には5件入るので、5件目の 7/28 は
「`((5-1) % 4) + 1 = 1`」という剰余で新ルーティンの1回目として出せていた。
しかし 8/7 は次の暦窓 `[7/31, 8/31)` に落ちるため件数が振り出しに戻り、
**7/28 から新ルーティンが始まっている事実が失われて**また 1 になっていた。
剰余のごまかしは1つの暦窓の中でしか成立しない。

**対処**: `getBookingProgressIndex` も `resolveEffectiveCycle`（＝`computePlanUsage` と同じ窓）で
数えるようにした。7/28 でロールして窓が `[7/28, 8/29)` になるため、8/7 は素直に2件目になる。
猶予の繰入数も `graceLentToPrevCount` を自前で呼ぶのをやめ、`resolveEffectiveCycle` が返す
`lent` を使う（繰入の判定を2箇所で持たない）。剰余は、同日に上限を超える予約が入って
窓を引き直せない場合の保険として残してある。

## 落とし穴
- **回数の表示を足すときは `resolveEffectiveCycle` を通す。**
  `getCycleWindow` を直接使うと、応当日をまたいだ瞬間にカウントが1に戻る。
- チップ側の呼び出しは `resolveCycleMonths` / `resolveGraceDays` を必ず渡すこと
  （`resolveGraceDays` は `profiles.grace_enabled=false` のお客様で0を返す）。
- 起算日より前の予約はどの窓にも入らないので `getBookingProgressIndex` は `null` を返す
  ＝チップが出ない。トレーナーが起算日をリセットした場合の過去分がこれに当たる（仕様）。
- 回帰テストは `src/test/courseProgress.test.ts` の
  「getBookingProgressIndex × 使い切り後のロール」。本番の実データをそのまま置いてある。

## 2026-10-15: 間が空いたあとの区切りを、1回目の日ではなく起算日の応当日で切っていた

宗本さん（予定表のスクリーンショット）「次回の1回目のトレーニング日が10/22やから11/22までで

起算日 10/6（固定なし）・月4回・猶予OFF・予約 10/22, 10/29, 11/5, 11/12 のお客様で、

1. チップ（`getBookingProgressIndex`）は保存された起算日の暦窓 `[10/6, 11/7)` `[11/7, 12/8)` で

- 引き直すのは**その1回目の日が referenceDate までに来ている場合だけ**。未来の予約で先回りして
  動かすと、猶予で前の区切りへ繰り入れた予約が区切りから外れて数えられなくなる

- 猶予の既存テスト2件は、データの1回目を起算日の当日（6/4）に寄せた。1回目が起算日より後

- 本番の全お客様（50人・チップ583個）を修正前後で再計算して、変わったのは:
  - チップ3個。どれも「1回目から1ヶ月」に揃う方向:

## 2026-10-15: レポートの期間もカードの「利用期間」に揃えた

宗本さん「（レポートの期間も）揃えて」。以前は月次レポートとホームの「今回のレポート（来店◯回）」が
保存された起算日からの1ヶ月ごと、部位バランスが暦の月（1日〜月末）で区切っていて、
今の区切りに予約があるお客様29人中13人で、カードの利用期間とずれていた。

`src/lib/reportPeriod.ts` の `reportPeriodAt(source, offset)` に集約した。

- **offset 0（今回）＝カードの利用期間そのもの**（`computePlanUsage` と同じ引数で解く。毎日分を突き合わせるテストあり）
- 前の期間は「区切りの1回目の日から、次の区切りの1回目の前日まで」。回数の区切りと同じなので、
  期間どうしは隙間も重なりもなく、どの来店もちょうど1つの期間に入る
  （本番50人・過去546期間で、期間の中のチップが 1, 2, 3… と並ぶことを確認）
  - 使い切りで次へ移った来店は次の期間（例: 9/15〜10/12 → 10/13〜）
  - 猶予で前回分に回した来店（チップの「前回分」）は前の期間に入れる
  - 区切りの間が数日空いただけなら、その日々は前の期間に含める（「7/24〜7/26」のような数日だけの期間を作らない）。
    1ヶ月以上空いたら、空いた月がそれぞれ1つの期間
  - 起算日より前は、1つ後の期間の開始日からプランの区切りの長さでさかのぼる
- **対象外は null を返し、画面は従来の期間を使う**: 回数券・期間プラン・起算日なし・カードを出さないプラン
  （部位バランスは暦の月、月次レポートは起算日からの区切りのまま）
- 部位バランスの表示は「今月／先月」→「今回／前回／N回前」、期間は「10/22〜11/22」（対象外は従来どおり）
- トレーナーのお客様詳細の部位バランスは、そのお客様の材料（カードと同じもの）を `periodSource` で渡す。
  渡さないとログイン中の人（トレーナー）の予約で期間を出してしまう
- 材料（プロフィール・予約）の読み込み中は読みに行かない（違う期間のデータを一瞬読まない）
- ついでに直したこと: 月次レポートのトレーナーコメントは `monthly_reports.month`（暦の月初）で探す。
  以前は期間の開始日そのもので探していて、開始日が1日でないお客様には一度も出ていなかった
  （本番の monthly_reports は0件だったので、影響が出た人はいない）
- 除外するプラン名（初回無料体験・プラン未設定）は `planUsage.ts` の `PLAN_USAGE_EXCLUDED_PLAN_NAMES` に移した
  （カードとレポートで共通。`trialPricing.test.ts` の内部キーの見張りも移し先を見る）

⚠️ 今の期間に「次の区切りの1回目」が未来の予約で入っている（使い切りが未来で起きる）ときは、
カードと同じ窓のままなので、月次レポートの「今回の予約予定」にその予約も数える（カードは上限で頭打ち）。
その日が来れば次の期間に移る。

## 2026-10-15: 予約カレンダーに「今回の利用期間」を出す

宗本さん「お客様が毎回、今回の期間はいつからいつまでかカレンダーに分かりやすく期間を表示する」。
期間外の日を選んだときの一言は「入れる」、店ごとの設定は作らない（お客様ごとの「利用期間の表示」に従う）。

- **帯**: 今回の期間のマスに薄いテーマ色、次の期間（予約がもう入っている／起算日固定で暦で決まっている）に薄い灰色。
  マス（td）の下地に敷くので「満」「残N」・自分の予約の丸印・今日／選んだ日の塗りはそのまま見える。
  前後の月の日（outside）には敷かない。過ぎた日にも敷く（いつ始まったか分かるように）
- **説明**（カレンダーの下）: 「今回の利用期間 10/8〜11/8（あと2回予約できます）」「次の期間 …」。
  1回目のご予約待ちは「利用期間は1回目のご予約日から始まります…」
- **一言**（日を選んだとき）: その日が新しい期間の1回目になるなら「この日から次の期間（…）になります」、
  決まっている次の期間なら「この日は…の期間の◯回目になります」。今回の分なら何も出さない
- **定期予約**: 途中の回から次の期間に入るなら「11/12（3回目）から次の利用期間になります」

🔴 押さえどころ:
- 期間は**カードと同じ計算**（`computePlanUsage`）。帯だけ別に数えない
- 「この日ならどの期間の何回目か」は**日付の範囲で決めない**。その日に予約が入ったと仮定して回数の計算に通す。
  使い切ったあとの期間内の日（＝次の期間の1回目）と、猶予の日（＝前回分）を日付だけでは必ず間違える。
  本番50人×60日（3,000日）で、一言とチップ（実際に入れたときの回数表示）が全部一致することを確認した
- **猶予の日は案内しない**（一言を出さない）。大目に見る運用で、店から勧めるものではない
- 使い切りが未来で起きる（次の期間の1回目がもう予約済み）ときは、今回の帯をその前日までにする。説明の日付はカードと同じ
- 日時の変更中は、動かす予約を除いて数える（残したままだと1回多く数える）
- 「利用期間の表示」が OFF のお客様には帯・説明・一言のどれも出さない
- 回数券・期間プラン・プラン未設定・体験は出さない
- 当日の閲覧専用の日（当日予約不可の店）には一言を出さない

`CustomerBooking.tsx` は行数の上限ぎりぎりなので、カレンダーの1日分（DayContent）を
`BookingCalendarDay.tsx` の `bookingDayContent` に移して行を空けた。

見張り: `src/test/calendarPeriod.test.tsx`（29件。変異7件が赤）。
